## 3. Неизменяемые договорённости владельца

1. **Магазин закрыт для покупателей**, пока владелец явно не разрешит открытие: `settings.shop.enabled=false`. Сохранять уже согласованные тексты/публичную заглушку (в дефолте: «Магазин скоро откроется»); не щёлкать переключатель, не переключать на `true` в production, не запускать реальные платежи и автоматически не передавать заказы поставщику.
2. **Утверждённый дизайн, фото тягача, карта, тексты, кнопки и маршруты** не меняются самовольно. Проверять `scripts/verify-approved.mjs`, мобильные и ПК скриншоты в CI, все рабочие кабинеты. Предложения по спорным изменениям — обсуждать до реализации.
3. Регион пилота: **Санкт-Петербург и Ленинградская область**; сервис для **грузовых автомобилей и грузовых прицепов/полуприцепов**. Не превращать в каталог легковых авто или другой бизнес.
4. При «продолжай» делать реальные изменения и тестировать после каждого изменения. Сохранять утверждённые решения; не выдавать мок-данные за работающую коммерческую интеграцию.
5. Клиент должен возвращаться в TrackSOS благодаря **простому, быстрому, удобному** магазину, а не работать через неудобный сайт поставщика.

## 4. Магазин: что уже реализовано в коде

- Групповой каталог для грузовых авто, прицепов/полуприцепов и универсальных деталей, поиск по **названию, производителю, артикулу, синонимам**; постраничные товары и ленивые фото.
- Привязка заказа к машине из **«Моего гаража»**, история покупок по машине, повторный заказ и переход к **проверенным кроссам/аналогам**. Кросс-номер **не равен** подтверждённой применяемости по VIN.
- Индекс артикула/названия для слабой сети в IndexedDB, загрузка небольшими порциями по выбору пользователя, дельта-обновления и удаление отозванных записей. Личные данные, VIN, цены, остатки и секреты поставщика не хранятся в текстовом офлайн-индексе.
- Изолированный **справочник без придуманных цен**: администратор импортирует лицензированный CSV/TSV, предварительно проверяет, загружает партиями, вручную подтверждает; неподтверждённое не продаётся. Проверенные справочные записи могут искать покупатели **только когда магазин в будущем будет разрешён к открытию**.
- **Автоконтинент** определён основным поставщиком. Подготовлены закрытые админские соответствия артикула TrackSOS и артикула Автоконтинента с отметкой источника. **Реальный API поставщика НЕ подключён**, каталожная выгрузка/права использования не получены, живые цены/остатки/покупки от Автоконтинента не работают.
- **Подбор по VIN** требуется, но ещё не внедрён как достоверная внешняя база применяемости. Для прицепов отдельно учитывать номер оси/агрегата, если одного VIN недостаточно. Нельзя утверждать, что деталь подходит по VIN, если это не проверено.
- Техническая спецификация: [docs/SHOP_CATALOG_LOW_DATA.md](docs/SHOP_CATALOG_LOW_DATA.md). Миграции `038_shop_catalog_history.sql` – `042_shop_reference_changes.sql`.
- Перед запуском магазина нужны лицензия на данные, проверенные цены, актуальные остатки, интеграция с поставщиком, договорные/юридические согласования и проверка возвратов/заказов. Никакого автоматического открытия.

## 6. Что делать В НОВОМ ЧАТЕ: безопасная проверка Timeweb перед релизом

**Сначала только читать состояние, ничего не изменяя.** На VPS через SSH или консоль Timeweb, без вставки паролей/номеров в переписку:

```bash
cd /root/traksos
pwd
git branch --show-current
git rev-parse HEAD
git status --short
git fetch origin
git rev-parse origin/main
cd deploy
bash ./doctor.sh
bash ./diagnose-sms.sh
```

- `git fetch` обновляет ссылки Git, но **не заменяет сайт и БД**.
- Если `doctor.sh` или `diagnose-sms.sh` ещё нет на VPS, это означает, что серверная копия кода может отставать. Не скачивать случайные скрипты; сначала проверить ветку и файлы.
- **Перед обновлением** отдельно получить актуальный HEAD `main` и убедиться, что GitHub Actions «Проверка» зелёная именно на него. Наличие успешной Android сборки или старого Docker image не заменяет эту проверку.
- В новом диалоге можно прислать **только вывод без токенов, паролей и ПДн**; следующий ассистент должен проверить возможные незакоммиченные изменения и безопасность.

## 7. Деплой на Timeweb — только после преддиагностики

Если `main` прошла CI, текущая ветка `main`, tracked-файлы на VPS не изменены и новый чат проверил риски:

```bash
cd /root/traksos
git status --short
git branch --show-current
git pull --ff-only origin main
bash deploy/verify-shop-closed.sh
bash deploy/update-site.sh
cd deploy
bash ./doctor.sh
bash ./diagnose-sms.sh
curl --fail --silent --show-error https://traksos.ru/api/health
```

**Защита магазина:** `deploy/update-site.sh` (после этой передачи) вызывает `deploy/verify-shop-closed.sh` **до резервного копирования/замены контейнера и после проверки нового API**. Если в живой БД `shop.enabled` не `false` или значение некорректно — обновление останавливается, **ничего автоматически не переключает**. Проверка read-only, скрытых настроек не печатает.

- Скрипт `update-site.sh` делает custom `pg_dump`, проверяет `pg_restore --list`, создаёт новый Docker app image и заменяет **только** app; PostgreSQL volume не удаляется, `.env` не перезаписывается.
- Бэкап на том же VPS **не заменяет внешнюю копию** и не гарантирует успешное восстановление. До важных боевых изменений нужен отдельный restore-test.
- После обновления подтвердить: `/api/health`, HTTPS, `docker compose ps`, `doctor.sh`, доступность домена, закрытый магазин, вход админа, SMS/восстановление, права кабинетов, дизайн/кнопки и реальные push на Android.
- **Если ошибка**: остановить дальнейшие действия; изучить только обезличенные строки `docker compose logs --tail=80 app`, `doctor.sh`. Не делать `docker compose down -v`, `git reset --hard`, ручной SQL-откат схемы или восстановление дампа поверх текущей БД без плана.
- Если VPS отстаёт слишком далеко, миграции идут автоматически при старте. Проверить совместимость и возможность резервного восстановления, потому что старый APK может обращаться к новому API.
