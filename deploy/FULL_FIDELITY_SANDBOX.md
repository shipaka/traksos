# TrackSOS — полноценные тестовые кабинеты с общим кодом

**Назначение:** администратор открывает настоящие React-экраны и рабочие API TrackSOS для клиента, владельца автопарка, сотрудника с ограниченными правами, мастера, эвакуатора, СТО и других ролей. Отличаются только **окружение, учётные данные и фиктивные данные**. Больше не поддерживаем отдельные визуальные копии кабинетов.

## Принцип единого источника

- **Один GitHub commit → один Docker image digest** для prod и sandbox. Оба сервера запускают **один и тот же фронтенд + backend из репозитория**, но их версии могут различаться: песочница обновляется и тестируется раньше prod. Полное совпадение экранов возможно при одном digest; при разных версиях это предварительный просмотр изменений, а не полная копия текущего prod.
- Админ выбирает роль в существующем `#/admin/test-center`, сервер проверяет точное совпадение совместимость протокола одноразовых приглашений и доступность отдельной базы, выдаёт одноразовое приглашение (45 с), а отдельный sandbox выпускает тестовую сессию (2 ч при прямом входе в обычную роль; 12 ч для административного браузерного супервизора и переключённых им ролей до срока истечения его допуска). Администраторский вход позволяет переключать все 12 вымышленных ролей через верхнюю панель без повторной регистрации; переключённый аккаунт не может выдавать себе новые роли. Продакшен никогда не выдаёт вход от лица реального клиента.
- Тестовая база `traksos_sandbox` и отдельный том `sandbox_db`. Никаких данных и ключей из `db` production. Пользователи — только вымышленные. Изолированные Docker сети не позволяют sandbox-app подключиться к production-db даже случайно.
- Sandbox `SMS_PROVIDER=log`, `PUSH_PROVIDER=log`, `PAYMENT_PROVIDER=mock`; публичная регистрация отключена; тестовые входы только с разрешения админа через отдельный сервер.
- Для карт используется **тот же компонент**: если соответствующая демонстрационная заявка содержит вымышленные координаты, карта и стадии работают как на настоящем сайте, но GPS администратора не запрашивается и реальная геолокация не отправляется. Для пустых сценариев нужны дополнительные сценарии/тестовые записи, не отдельный UI.
- Локальные старые тренажёры остаются временным fallback **с явной маркировкой**, пока полнофункциональный стенд не развернут; они не являются доказательством поведения production.

## До запуска

1. Проверить текущую резервную копию production и статус `main`. **Никогда не использовать production DB dump для наполнения sandbox.**
2. Создать DNS A для `sandbox.traksos.ru` на IP VPS, дождаться HTTPS. Подготовить отдельный `deploy/.env.sandbox` из шаблона и задать уникальный APP_SECRET. В `deploy/.env` задать `SANDBOX_DOMAIN=sandbox.traksos.ru`, `SANDBOX_DB_PASSWORD` (свой отдельный секрет), `SANDBOX_URL=https://sandbox.traksos.ru` и идентичный с sandbox `SANDBOX_SHARED_SECRET`. Секреты не копировать в чат/GitHub.
3. Собрать один образ **из релизного commit**: в обычном VPS-обновлении `TRAKSOS_RELEASE_REV=$(git rev-parse HEAD)` и аргумент Docker `BUILD_REV` дают контрольную версию. Если используете GHCR — брать тег `ghcr.io/shipaka/traksos:<полный_SHA>`, не плавающий latest; digest сравнить до релиза.
4. Поднять отдельную БД и приложение, используя overlay `docker-compose.sandbox.yml`. Важно: `sandbox-app` **не должен** оказаться в `deploy_default`, где находится production DB. Для связи с Caddy подключить **только Caddy** к `deploy_sandbox_public` (`docker network connect`, если ещё не подключён). Имя сети проверить через `docker network ls`; оно зависит от Compose project name.
5. Только после проверки сети/отсутствия реальных секретов запустить инициализацию `node --import tsx server/src/seedSandbox.ts` **в контейнере sandbox-app**. Она сама откажется работать без `SANDBOX_INSTANCE=true`. После этого в sandbox появятся фиктивные машины/исполнители.
6. Добавить блок из `Caddy.sandbox.snippet` в основной `Caddyfile` **только когда sandbox готов**, проверить `caddy validate`, перезагрузить конфигурацию. Никаких изменений настоящего публичного `traksos.ru` или базы.
7. Пройтись по ролям и всем действиям, проверить, что `https://sandbox.traksos.ru/api/health` возвращает `sandbox:true`, `db:true`, поддерживаемый `sandboxHandoffVersion` и отдельную здоровую БД; `buildRevision` может отличаться от prod. Вход в режим через **админку production**, а не публичную регистрацию.
8. При следующих релизах `update-site.sh` должен использовать **тот же Docker image** для обоих контейнеров, проверять одинаковый SHA и доступность стенда. Пока стенд не развёрнут, автоматическое переключение ещё не работает и роль остаётся в состоянии «тестовый сервер не подключён».

## Критерии приёмки

- Скриншоты 390px / 1440px тестового и настоящего кабинетов совпадают по DOM/CSS/визуалу при одинаковом состоянии, включая карту, навигацию и вызовы.
- Тестовую заявку можно создать, принять, провести по статусам и закрыть **только разрешёнными ролями**, а повторно войти в ту же тестовую сессию можно без повторной регистрации до истечения.
- В `production.orders`, `production.users`, `production.ledger_entries` до и после теста **нет изменений** от тестового режима.
- Заявки и тестовые выплаты видны только внутри sandbox. Реальные SMS, деньги, push, активация магазина и юридические процессы не запускаются.
- Если sandbox упал, отсутствует отдельная БД или несовместим протокол входа — **вход блокируется**, а не подменяется учебной имитацией. Разные версии приложения допустимы при совместимом защищённом протоколе.
- CI + E2E по каждому типу кабинета на фиктивных аккаунтах; покрыть успешный вход, повторную попытку одноразового токена, истечение и проверку ролей.

**Статус:** код ветки — подготовительная реализация; перед подключением тестового DNS/VPS обязательны CI, реальная проверка отдельной сети/БД, ролей и ручная приёмка. Ничего не выкатывать напрямую из PR.

## Совместимый вход при разных версиях (обновление 2026-11-17)

Рабочий сайт (`traksos.ru`) после **отдельного одобренного обновления** предоставляет администратору раздел «Тестирование кабинетов». Администратор выбирает роль; сайт проверяет адрес песочницы, `sandbox=true`, `db=true`, `ok=true` и `sandboxHandoffVersion=1`. Если протокол совместим, выдаёт короткий подписанный билет (45 секунд), после чего браузер **в той же вкладке** переходит на `sandbox.traksos.ru`, где билет обменивается на отдельную тестовую сессию. Есть возврат в админку по отдельной ссылке. Один только ручной переход на sandbox не даёт административного входа.

**Новая модель релизов:** sandbox может использовать новый SHA, а production — прежний. Это намеренное отличие от старого строгого сравнения `buildRevision`. Билет всегда остаётся HMAC-подписанным, одноразовым, ограниченным по времени и роли; настоящие токены/клиенты с production в песочницу не передаются. При изменении формата/семантики билета требуется увеличить `SANDBOX_HANDOFF_PROTOCOL` и обновить оба окружения совместимо. Переход не означает автоматическое обновление prod.

**Важно:** до первого обновления обоих сервисов до совместимого протокола этот маршрут может быть недоступен. Изменение кода в GitHub **не меняет уже запущенный VPS**, автоматическую выкладку на VPS необходимо настроить отдельно, без расширения прав read-only мониторинга.
