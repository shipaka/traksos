# TrakSOS / Timeweb — безопасное обновление из НОВОГО ЧАТА
**13.11.2026.** Инструкция для существующего VPS, НЕ для установки проекта с нуля. Основа: [../NEXT_CHAT_TRACKSOS.md](../NEXT_CHAT_TRACKSOS.md).

## Жёсткое правило перед работой

Сайт и база могут уже обслуживать пользователей. Ни один шаг здесь не должен заново создавать VPS, роли, учетные записи или `deploy/.env`. Не пересоздавать Docker volumes. **Магазин остаётся закрытым** (`settings.shop.enabled=false`), его тексты/дизайн не трогать. Скрипт `verify-shop-closed.sh` теперь обязателен до и после обновления.

Данные о сервере: ранее использовался Timeweb, каталог **`/root/traksos`**, основной домен **`traksos.ru`**. Фактическая ревизия на сервере на момент создания этого файла не проверена: новый чат должен сверить её в первую очередь.

## Шаг А: безопасная диагностика — сайт не меняем

Войти в Timeweb SSH/консоль, выполнить на самом VPS:

```bash
cd /root/traksos
pwd
git branch --show-current
git rev-parse HEAD
git status --short
git fetch origin
git rev-parse origin/main
cd deploy
bash ./doctor.sh
bash ./diagnose-sms.sh
```

Вывод `doctor.sh` специально скрывает секреты, но перед передачей в чат всё равно просмотреть его и убрать номера/ключи, если они вдруг возникли в сторонних ошибках.

**ОСТАНОВИТЬСЯ**, если каталог не тот, не `main`, есть незакоммиченные изменения в tracked-файлах, проблемы с БД/диском/контейнерами, неожиданно открыт магазин или отсутствует нормальный резервный архив. Не использовать `reset --hard`, чтобы «исправить» грязный каталог.

Параллельно новый чат смотрит https://github.com/shipaka/traksos/actions и сравнивает **актуальный SHA `origin/main`** с последним завершённым зелёным `Проверка`. Для Android при изменении интерфейса — зелёный `Android` с тем же UI; для server image — зелёный `Образ сервера` на проверенном SHA. Для старых коммитов зелёные workflow недостаточны.

## Шаг Б: обновление кода и защита магазина

**Только после Шага А и сверки CI**:

```bash
cd /root/traksos
git status --short
git branch --show-current
git pull --ff-only origin main

# Только чтение БД; останавливается, если магазин открыли/повредили настройки:
bash deploy/verify-shop-closed.sh

# Создаёт и проверяет PostgreSQL backup ПЕРЕД заменой app-контейнера:
bash deploy/update-site.sh
```

- `update-site.sh` проверяет Docker Compose, запуск PostgreSQL, наличие закрытого `.env`, отсутствие tracked-изменений и **закрытый магазин**.
- Он делает `pg_dump -Fc` в `deploy/backups/pre-release-*.dump`, проверяет архив через `pg_restore --list`, **строит новый app image до замены** и затем `docker compose up -d --no-deps app`. PostgreSQL `db`, `caddy` и `backup` не пересоздаются.
- Ждёт успешный запрос внутреннего `/api/health`, затем **ещё раз** проверяет `shop.enabled=false`. Если проверка не прошла, выпуск считается неудачным и нужно разбираться с причинами, **не** выполнять ручной SQL rollback «наугад».
- Обычное обновление кода может запустить миграции приложения. Сначала проверить бэкап и запас места; внешняя резервная копия и пробное восстановление на отдельной БД остаются обязательными до обработки реальных данных.

## Шаг В: после обновления

```bash
cd /root/traksos
git rev-parse --short HEAD
bash deploy/verify-shop-closed.sh
cd deploy
bash ./doctor.sh
bash ./diagnose-sms.sh
docker compose ps
curl --fail --silent --show-error https://traksos.ru/api/health
```

Проверить на телефоне и ПК: главную TrakSOS, утверждённую фуру/карту, вход, роли, личные кабинеты, меню/кнопки, страховку/ТО, гараж, админский тренажёр 10 кабинетов (`#/admin/test-center`), **магазин с прежней заглушкой**, отсутствие заказа/оплаты при закрытом магазине. Если есть тестовые учётные записи на отдельном стенде — проверить с ними; **не использовать настоящие клиентские заявки для регрессий**.

Проверить отдельно (по одному без спама): доставку SMS.ru на свой номер, восстановление доступа, рабочую подпись отправителя; RuStore Push на физическом Android в фоне, закрытом экране и после блокировки; совпадение ключа подписи Android APK при установке обновления. Коды и ключи не публиковать.

## Если что-то пошло не так

- До замены app: проверить сообщение скрипта, никакой необходимости трогать БД или тома нет.
- После замены app: сохранить точную ошибку/момент, без личных данных; посмотреть `cd /root/traksos/deploy && docker compose logs --tail=80 app` **только после очистки секретов**, `docker compose ps`, `bash ./doctor.sh`.
- Не делать `docker compose down -v`, `docker volume rm`, `pg_restore --clean`, `git reset --hard`, не удалять `backups`, не пересоздавать `.env`.
- Восстановление БД допускается только как отдельная контролируемая процедура после исследования схемы, текущих транзакций и точки восстановления. Старый образ приложения может быть несовместим с уже применёнными миграциями; **не считать ручное переключение Docker image безопасным rollback**.

## Что новый чат должен зафиксировать в отчёте

- SHA `main` GitHub и SHA на VPS **до/после**.
- Результат CI именно на развёрнутом SHA.
- Успешность `pg_dump`, валидность архива, наличие внешней копии (если проверено).
- `docker compose ps`, `doctor.sh`, HTTPS /api/health.
- **Отдельно** подтверждение, что магазин закрыт ДО и ПОСЛЕ.
- Состояние реальной доставки SMS и кабинета администратора.
- Какие аппаратные/юридические проверки ещё не выполнены.
- Никаких заявлений «всё готово к публикации» по одному зелёному CI.
