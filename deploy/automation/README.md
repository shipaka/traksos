# TrackSOS — безопасная диагностика через GitHub Actions

## Что добавлено

- Ручной workflow «TrackSOS — проверка сервера и песочницы» (.github/workflows/observe-sandbox.yml).
- Проверка публичных HTTPS health endpoints без SSH — доступна после включения workflow в main.
- Дополнительная проверка контейнеров и разделения сетей VPS по SSH. Не запустится, пока отдельно не настроен ограниченный доступ и в форме не выбран include_server.
- Фиксированный серверный скрипт deploy/automation/health-report.sh: только чтение состояния четырёх известных контейнеров и сравнение Docker-сетей. Он не печатает переменные окружения, дампы БД, логи или ключи и ничего не изменяет.

**Это пока НЕ автоматическое обновление песочницы.** Обновление следует подключать отдельно, когда защищённая диагностика заработает и будет подтверждён независимый бэкап/проверка health. Production не обновляется этим workflow.

## Включение первой проверки без доступа к VPS

1. Просмотреть и объединить PR после CI.
2. Открыть GitHub → Actions → «TrackSOS — проверка сервера и песочницы» → Run workflow.
3. Сначала не включать include_server: будут проверены только HTTPS endpoints traksos.ru и sandbox.traksos.ru.
4. По журналу запуска определить HTTP-статусы. Это ничего не меняет.

## Подключение SSH (один раз, отдельная операция администратора)

Используйте только проверенный репозиторий/коммит на VPS. **Не передавайте приватный SSH-ключ, пароли или токены в чат, в PR, в логи или в git.**

1. После ревью/слияния PR и сверки чистого Git-дерева VPS аккуратно получить одобренный main без перезапуска приложения. Проверить, что нужная версия скрипта существует в /root/traksos/deploy/automation/health-report.sh.
2. От имени администратора установить его как /usr/local/sbin/traksos-health-report, **владение root:root и режим 0755**. Убедиться, что traksos-monitor не может изменять файл и родительский каталог. Скрипт не должен принимать аргументы для произвольного выполнения.
3. Создать отдельного пользователя traksos-monitor. **Не** добавлять его в группы docker или sudo, не разрешать обычный root SSH-вход. Для чтения Docker дать через /etc/sudoers.d/traksos-monitor строго одну команду:

   traksos-monitor ALL=(root) NOPASSWD: /usr/local/sbin/traksos-health-report

   Проверить sudoers через visudo -cf, а права файла выставить 0440.
4. Сгенерировать отдельную SSH-пару Ed25519 для мониторинга на доверенном устройстве. Публичный ключ поместить в /home/traksos-monitor/.ssh/authorized_keys с ограничителями **на той же строке перед ключом**:

   restrict,command="sudo -n /usr/local/sbin/traksos-health-report" ssh-ed25519 AAAA...

   Здесь AAAA... означает **свой реальный публичный ключ**, а не текст для вставки. Режимы: .ssh — 0700, authorized_keys — 0600, владелец — traksos-monitor. Применять только после проверки прав и синтаксиса; иначе возможна блокировка нового подключения.
5. Подтвердить SSH host key сервера из доверенного источника, а не бездумно принимать первый предложенный ключ. В репозитории GitHub → Settings → Secrets and variables → Actions создать:
   - TRAKSOS_MONITOR_HOST — адрес VPS;
   - TRAKSOS_MONITOR_PORT — порт SSH (можно не задавать, тогда 22);
   - TRAKSOS_MONITOR_PRIVATE_KEY — приватный ключ **только для этого ограниченного пользователя**;
   - TRAKSOS_MONITOR_KNOWN_HOSTS — проверенная строка known_hosts, соответствующая имени и порту, по которому выполняется подключение.
6. Запустить workflow на ветке main с include_server = true. В журнале должны быть статусы контейнеров и результат проверки изоляции сетей, **без** содержимого .env и БД.

В публичном репозитории не рекомендуется разрешать ненадёжным pull request workflow с доступом к SSH secrets. Данный workflow вызывается вручную, а SSH job запускается только на main. Для будущих деплоев использовать отдельно защищённые GitHub Environments, минимальные права и обязательное подтверждение выпуска в production.

## Важные ограничения

- Docker socket предоставляет фактически привилегии root. Именно поэтому **нельзя** выдавать пользователю мониторинга доступ к docker group; sudo разрешает только фиксированный root-owned диагностический скрипт.
- Нельзя публиковать в GitHub Actions сырой docker inspect с полным .Config.Env, текст .env, дампы, приватные ключи или содержимое логов, где могут оказаться пользовательские данные.
- Проверка разделения сетей показывает отсутствие общей Docker-сети между sandbox-app и production-db. Она **не** заменяет аудит всех сетевых правил, ключей и путей к БД.
- Даже зелёная диагностика не доказывает готовность релиза: требуются реальные тесты входа, SMS, резервного восстановления, независимых баз и проверка миграций.
- Никаких docker compose down -v, docker volume rm, автоматического pg_restore или переключения production на latest.
