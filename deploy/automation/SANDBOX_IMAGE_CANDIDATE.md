# TrackSOS — проверка нового образа на изолированной песочнице GitHub

Workflow: `.github/workflows/sandbox-image-gate.yml`.

После успешной публикации в GHCR Docker-образа из ветки main тест запускается автоматически; его также можно запустить вручную из main.

- Берётся образ по **полному SHA коммита**, не `latest`.
- Docker Compose поднимает `sandbox-db` и `sandbox-app` **только на одноразовом GitHub-hosted runner**, используя отдельную PostgreSQL и внутренние Docker-сети.
- Генерируются случайные секреты **только в CI**. Номера телефонов — фиктивные, а SMS, push и оплата принудительно отключены (`log/log/mock`).
- Проверяется настоящий HTTP-эндпоинт `/api/health`: `ok=true`, `db=true`, `sandbox=true`, `buildRevision=SHA`.
- Контейнеры и конфигурация уничтожаются вместе с эфемерным CI runner. Отчёт находится в GitHub Actions.

**Строгая граница:** этот workflow не обращается к VPS и не развёртывает ни production, ни существующую песочницу `sandbox.traksos.ru`. Он подтверждает лишь совместимость нового образа с **чистой тестовой БД**, не совместимость со старой действующей БД и не проход всех пользовательских сценариев.

## Прежде чем включать автоматическую выкладку настоящей песочницы

Существующая песочница — отдельный Compose-проект `traksos-test` в `/root/traksos-sandbox`, а не overlay рабочего проекта `deploy`. Требуется отдельный защищённый deploy-ключ и root-owned ограниченный обработчик **только этого Compose-проекта**, со строгим SHA, верификацией GHCR digest, явными preflight-guards, резервной копией **песочницы** и проверкой уже существующей схемы/миграций.

Нельзя: расширять права существующего `traksos-monitor`, подключать песочницу к production-базе, стирать локальные правки Caddy или Compose, использовать `git reset --hard`, запускать `deploy/update-site.sh` для текущего раздельного стенда, обновлять production автоматически либо бездоказательно откатывать миграции базы.

Развёртывание на VPS **не активировано** этим workflow, дополнительных GitHub Secrets для этой проверки не нужно.
