# TrackSOS · P0: безопасная выкладка в реальную песочницу

Issue [#133](https://github.com/shipaka/traksos/issues/133), координация [#132](https://github.com/shipaka/traksos/issues/132).

## Что готово в этом PR

Только **сценарий диагностики без изменения данных** `sandbox-vps-readonly-preflight.sh`, отдельно от уже работающего `traksos-monitor`. Он рассчитан на фиксированную существующую песочницу `/root/traksos-sandbox`, сервисы `traksos-test-sandbox-app-1` и `traksos-test-sandbox-db-1`:

- проверяет наличие checkout, отдельного sandbox Compose-файла и `.env.sandbox` (без чтения/публикации содержимого);
- сравнивает состояния ожидаемых Docker-контейнеров и общих Docker-сетей/томов между sandbox и production;
- проверяет публичные HTTPS `/api/health` двух доменов, `db`, `sandbox` и `buildRevision`;
- возвращает **код ошибки** при отсутствии любой важной гарантии; никогда не считает предупреждения разрешением на deploy.

Скрипт не устанавливается на VPS из GitHub автоматически, не вызывается мониторным SSH-ключом, не запускает миграции, не использует `docker compose up/down`, `git pull` или `pg_dump`, не меняет ни один контейнер/секрет. Изначальный `traksos-monitor` остаётся исключительно read-only.

## Отдельный следующий PR после достоверной инвентаризации

1. Создать **отдельного пользователя** с отдельной SSH-парой ключей для sandbox deploy, доступ только к одной root-owned программе, с запретом shell/port forwarding и без группы docker. Мониторный ключ не использовать.
2. Скрипт из разрешённого fixed path принимает **только полный SHA** уже проверенного GHCR-образа, строго проверяет `/root/traksos-sandbox` и проект `traksos-test`.
3. Перед обновлением проверяет чистоту необходимых файлов, статус sandbox DB и валидный архив **отдельной sandbox БД**. Проверка архивного формата не равна полной проверке восстановления.
4. Неизменяемые конфиги и volumes production сохранить; не трогать `/root/traksos`, общий `deploy/Caddyfile`, production networks, credentials и data.
5. Получает ровно разрешённый image SHA из GHCR, проверяет digest, меняет **только sandbox-app**, проверяет health and buildRevision. При неудаче останавливает процесс с отчётом, не предпринимает SQL rollback.
6. При первой установке механизма входа #131 нужен **отдельно одобренный** релиз на production и sandbox; после него sandbox может быть новее.

### Почему не включено автоматическое обновление прямо сейчас

GitHub не имеет write-доступа к VPS через текущий ключ — и это правильно. До подтверждения фактической конфигурации отдельного Compose-проекта нельзя безопасно писать автоматический updater, способный воздействовать на работающий сайт. Этот PR фиксирует проверяемую исходную точку без попытки обойти защиту.

**Статус:** подготовленный read-only preflight. Ни песочница, ни production **ещё не обновлены**.
