# TrackSOS — Агентские закупки: финальная инженерная передача

Дата: 17.11.2026. Ветка: `feature/shop-agency-evidence-ledger-20261117`, PR #139.

## Единое ядро
Основой **выбранной технической реализации** является `shop_agency_*` (PR #139).
Это связано с реальными позициями `shop_orders`, админскими маршрутами,
документами, версиями доказательств и интерфейсом. В PR #138 остаётся другое,
пока неподключённое ядро `shop_agent_ledger_*`. **Никогда не накатывать обе
схемы в одну рабочую систему как два независимых источника истины.** PR #138
не менять автоматически; его полезные идеи корректировок перенесены в выбранную
схему, включая новый ссылочный механизм сторно.

## Функционально завершённый изолированный модуль
- Снимок договорённой суммы заказа, налогово нейтральные режимы:
  `client_purchase_agent`, `supplier_sales_agent` (требует договора),
  `own_inventory_sale`; базовые поручения/версии условий.
- Приватная первичка PDF/JPEG/PNG в БД с SHA-256,
  разнесение многострочных документов на позиции, проверка оригиналов и
  защита от подмены реквизитов файла.
- Отдельные денежные события, частичные сторно с обязательной ссылкой на
  исходный платёж и основанием. Сумма всех сторно одного платежа ограничена
  суммой исходного события; исходная запись не меняется.
- Автоматическая переоценка доказательств и инвалидирование старых внутренних
  подтверждений при любом новом файле, событии или сопоставлении с банком.
- Отчёты по суткам МСК, диапазонам, компаниям/ИНН, поставщикам; CSV с
  экранированием формул; архивные JSON-манифесты со SHA-256.
- Ручная загрузка **только нормализованных** CSV банка, дедупликация
  `account_ref + transaction_ref`, сверка по сумме/дате/потоку/реквизиту
  и проверенному оригиналу, неизменяемые отмены ошибочных связей.
- Всё закрыто на уровне API для роли admin; публичные/партнёрские
  маршруты не получают закупочную стоимость и банковские реквизиты.

## Порядок миграций, согласованный с актуальным main
На текущем `main` используются номера 116–118 для realtime/SOS.
Поэтому внедряем изолированные миграции, не переиспользуя их номера:

1. `119_shop_agency_evidence.sql` — базовые кейсы, документы, распределения, события, проверки.
2. `120_shop_agency_evidence_integrity.sql` — неизменяемость, версия доказательств, архивные снимки.
3. `121_shop_agency_bank_reconciliation.sql` — неизменяемые нормализованные выписки, строки и сопоставления.
4. `122_shop_agency_cash_corrections.sql` — ссылочные частичные сторно с причинами.

Миграции автоматические, одноразовые, через `schema_migrations`. Перед
боевым запуском сделать резервную копию и отдельный прогон на точной копии
PostgreSQL; нельзя вручную переименовывать уже применённую в иной ветке миграцию
в существующей базе. На `main` этих четырёх миграций до объединения не было.

## Проверки
- В GitHub CI: реальные PostgreSQL-интеграционные тесты,
  проверки типов, web build, браузерные сценарии, Android эмулятор.
- Сценарий на 1000 авторизованных сессий разных ролей в disposable PostgreSQL:
  одновременное открытие кабинетов, несколько волн SOS и обращений,
  права доступа, метрики p50/p95/p99 и согласованность старого ledger.
- Отдельно проверяются источники денег, дубли банковских транзакций,
  конкурентные сопоставления, SQL-триггеры, ограничения частичных сторно,
  доказательные архивы и блокировка доступа обычных клиентов.
- Это не тест 1000 оплат одновременно и не замена проверки VPS.

## Блокеры только для LIVE-использования
**Ни один из следующих пунктов НЕ подразумевает, что внутренняя разработка
незавершена, но каждый необходим до приёма реальных денежных сумм:**

- Юридическое и бухгалтерское согласование договора агентирования, начислений,
  комиссий и правил учёта на УСН/НДС; одобрение методики для КУДиР.
- Утверждённые версии оферт, действительные поручения клиентов, оригиналы ЭДО,
  актов, отчётов агента и платёжных поручений.
- Контролируемые интеграции с поставщиком «Автоконтинент» и банком,
  сопоставление оплаченного/поставленного; автоматические источники по API
  пока **не подключены**.
- Защищённое хранение и резервное копирование финансовых документов,
  разграничение ролей, 152-ФЗ, проверка восстановления базы.
- Отдельная приёмка на VPS и устройство клиента; не включать магазин
  или изменение реальных платежей автоматически.

**Доказательный реестр не формирует юридическую налоговую базу
(`taxableRevenue=null`), КУДиР и налоговую декларацию.**
