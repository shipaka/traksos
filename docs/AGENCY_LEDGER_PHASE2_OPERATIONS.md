# TrackSOS · Агентские закупки: этап 2 — целостность доказательств

**Область:** продолжение изолированного PR #139. Не активирует магазин, не создаёт внешних платежей, не интегрируется с «Автоконтинентом». Не сливать автоматически с параллельным PR #138: там другое ядро `shop_agent_ledger_*`; **для релиза должно остаться одно решение**, не две параллельные бухгалтерские книги.

## 1. PostgreSQL — ограничения на первичку

Миграция `117_shop_agency_evidence_integrity.sql` добавляет:

- запрет SQL `UPDATE/DELETE` для событий `shop_agency_events`, распределений `shop_agency_allocations`, подтверждений `shop_agency_reviews` и архивных снимков; исправления — **новыми** событиями и отдельными объяснениями;
- запрет удаления доказательных кейсов; изменение согласованной цены, ИНН, модели сделки, версии условий и прочих полей кейса невозможно; разрешён **только** рост `evidence_version` на 1 при новом доказательстве;
- документы запрещено удалять и переписывать, включая исходный `bytea`, SHA-256, реквизиты и сумму. Единственное разрешённое изменение — однократная ручная проверка с идентификатором администратора, датой и текстовым основанием;
- приватные, неизменяемые `shop_agency_report_snapshots` с ключом идемпотентности, датами, JSON-манифестом и SHA-256.

SQL-триггеры — защита от программных ошибок и обычных административных SQL-операций, **не** от суперпользователя PostgreSQL или злоумышленника с прямым доступом к хосту. Обязательны отдельные роли PostgreSQL, резервное копирование, аудит, контроль прав и проверка восстановления.

## 2. Подтверждение денег только через источник

В форме «денежное событие» вводится `sourceRef` (например, идентификатор транзакции банка). **Один этот текст ничего не доказывает.** Для допуска кейса к `verified` по каждому денежному событию нужен:

1. Загруженный оригинал типа `payment_proof` в PDF/JPEG/PNG, изначально `manual_unverified`.
2. Реквизит `reference`, **полностью совпадающий** с `sourceRef` денежного события; один документ банка может содержать несколько транзакций с одним общим номером, когда это соответствует оригиналу.
3. Распределение документа на конкретный финансовый кейс (`shop_agency_allocations`), даже если нулевое по сумме.
4. Ручная проверка файла с замечанием и аудитором.

При отсутствии источника выдаётся `awaiting_docs`, а запрос проверки блокируется. Даже у ранее проверенного кейса новые выплаты/возвраты немедленно повышают `evidence_version` и делают предыдущие подтверждения неактуальными.

Для импортируемых файлов `sha256` является идемпотентным только **при полном совпадении реквизитов**. Если тот же файл приходит с иной суммой, датой, видом, НДС, поставщиком или номером — HTTP 409, существующая первичка неизменна.

## 3. Правильные периоды и отсутствие двойного счёта

Для `/api/admin/agency/report` и CSV:

- **Денежные события** учитываются по `occurred_at` (фактические сутки МСК).
- **Суммы закупки, количество и входной НДС** отражаются по дате `issued_at` оригинала закупочного документа.
- **Согласованная цена и потенциальное вознаграждение** учитываются в периоде **создания доказательного кейса** как договорные снимки, а не как налоговый доход.
- В реестр попадает кейс, если в периоде есть хотя бы одно соответствующее событие, первичный документ закупки или создание кейса.
- Статусы `verified/accountant_approved` — **на текущую дату просмотра**. Отчёт не делает ложных утверждений, что документы были проверены в прошлом периоде.
- Группировки по заказам, компаниям/ИНН и поставщикам согласуются с общей сводкой. Период может пересекать календарные месяцы; дата проверяется по реальному календарю. Количество кейсов ограничено 2000 вместо молчаливого усечения.

Пример: документ УПД от 15 ноября 2026 на 10 000 ₽, приход денег 1 декабря 2026 на 13 650 ₽. В ноябрьский реестр попадает факт закупки; в декабрьский — приход денег. Закупка **не** показывается второй раз в сумме декабрьских закупок. Разница **не** превращается в налоговую базу автоматически.

## 4. Архив манифестов — не ФНС

- POST `/api/admin/agency/snapshots` с `{from,to,requestKey,note}`: создаёт неизменяемую копию агрегатов и машиночитаемую цепочку SHA-256 файлов / ID событий / ID версий согласований. Тот же ключ и те же данные → тот же ID, конфликтующий повтор → 409.
- GET `/api/admin/agency/snapshots`: последние 100 архивных снимков, только администратору.
- GET `/api/admin/agency/snapshots/:id`: архивный JSON-манифест, только администратору.
- `manifestSha256` рассчитывается по канонически упорядоченным фактам текущего запроса; изменение первички/событий изменит контрольную сумму нового снимка, не меняя сохранённый.
- Никаких фото первички в JSON-манифесте: только хеши/ссылки на оригиналы в защищённой БД. **Это не подписанный документ, не ЭДО, не КУДиР, не декларация и не готовый пакет для налоговой.**

## 5. Новые проверки

`server/test/shopAgencyLedger.test.ts` дополнительно проверяет:

- повтор SHA-256 с конфликтующей суммой и отсутствие понижения проверки при идемпотентном повторе;
- блокировку прямых SQL UPDATE/DELETE, неизменяемость прежнего архива после возврата;
- отказ в `verified` без проверенного банковского доказательства каждого платежа;
- разделение дней УПД и банковского события в разных отчётных периодах;
- одинаковые и конфликтующие ключи архивного экспорта;
- доступ к снимкам только у `admin`;
- невозможные даты, неизменную `taxableRevenue=null`.

Все прогоны — **после** отправки пакета, на disposable PostgreSQL. Финансовую нагрузку 1000 пользователей не проводить на production. Прежде чем подключать действующие заказы, нужны юрист/бухгалтер, подтверждённые оферты, первичка, API и отдельная миграционная стратегия после разрешения конфликта PR #138/#139.
