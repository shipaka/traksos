# Согласованный дизайн TrackSOS — правило разработки

Дата: 12 ноября 2026.

## Зафиксированное требование владельца
Если владельцу показан вариант оформления и он его утверждает, показанный вариант становится спецификацией реализации. Нельзя заменять его собственным дизайном, другими цветами, структурой или «упрощённым аналогом» без отдельного согласования.

## Эталон для ПК
- Первый утверждённый широкий экран TrackSOS: тёмно-синяя шапка и левое меню, светлая центральная область, крупный баннер с грузовиком и SOS, четыре компактные карточки разделов, реальные заявки и документы, правая панель помощи и уведомлений.
- Проверяемая HTML-версия с сохранённой разметкой и оформлением: `web/public/approved-desktop.html`.
- Соответствующий браузерный снимок передан владельцу в чате 12 ноября 2026.

## Правила выполнения
1. Не менять согласованную композицию, палитру, изображения, типографику и расположение блоков без явного подтверждения владельца.
2. Показывать скриншот **запущенного кода**, а не картинку-концепт. Подписывать скриншоты демо и реальные экраны честно.
3. Не использовать вымышленные заявки, полисы, платежи, телефоны и адреса как реальные данные. Демо отмечать явно.
4. Сохранять маршруты, API и доступы из действующего приложения и не заявлять об их работоспособности без проверки.
5. Проводить сверку скриншотов с эталоном до сообщения «готово».
6. Не считать самостоятельную HTML-страницу интеграцией в React-приложение, пока она не интегрирована и не проверена.

## Следующая задача
Перенести утверждённый компьютерный интерфейс из статической страницы в компоненты `web/src`, подключить настоящие данные API и затем снять скриншот работающего приложения на разрешении 1672×941.

## Регион запуска — жёсткое ограничение
- До расширения фактическая зона выездной помощи — **Санкт-Петербург и Ленинградская область**, не вся Россия.
- Нельзя показывать на главной общероссийскую карту, маршруты перевозок, рейсы, международную логистику или «покрытие по РФ» как существующие услуги.
- Если делаем карту, она должна быть региональной (Санкт-Петербург и Ленобласть) и показывать **только реальные** подключённые сервисы, актуальных мастеров и заявки, полученные через API; при отсутствии данных — понятное пустое состояние.
- Не придумывать номера заявок, статистику, позиции, рейтинги, адреса и количество исполнителей. Любые примеры явно помечать как демонстрационные.
- Расширение географии показывать только после фактического запуска в новых регионах и согласования с владельцем.


## ОКОНЧАТЕЛЬНО УТВЕРЖДЕНО ВЛАДЕЛЬЦЕМ (12 ноября 2026, последнее согласование)
Эта версия имеет приоритет над всеми более ранними дизайнами и демонстрационными страницами.

1. **Публичная главная на ПК до входа:** именно **ПК-экран со второй трёхчастной сравнительной картинки** `a_wide_composite_marketing_layout_with_three_panel.png` (изображение слева). Тёмно-синяя шапка, заметный брендированный грузовик TrackSOS, Петербург как ненавязчивый фон, реальный набор дорожных услуг, небольшая региональная демонстрационная карта, описание возможностей, вход/регистрация и промо мобильного приложения. Визуал — не личный кабинет.
2. **Android splash:** именно **средний телефон на ПЕРВОЙ трёхчастной картинке** `a_single_composite_promotional_layout_showing_thre.png`, а не похожая картинка из второй. При запуске — минималистичная загрузка на тёмном фоне: логотип TrackSOS, фура с брендингом, неброский Петербург, тонкий индикатор прогресса, без тяжёлых форм, услуг, заявок или действия «Начать». Не держать заставку после открытия сайта.
3. **Публичная мобильная версия сайта до входа:** **последняя отдельная картинка телефона** `a_highly_detailed_realistic_mockup_of_a_smartphon.png`: крупная фирменная фура, тёмно-синий фон, яркий SOS, **вход и регистрация сразу на экране** (вверху и/или рядом с SOS), реальные дорожные услуги, блок приложения; не экран авторизованного пользователя.
4. **Магазин приложений — только RuStore**. Никаких Google Play и App Store (даже как концептуальных ссылок). Пока карточка приложения в RuStore не опубликована, ссылка НЕ должна вести на несуществующую страницу: показывать «Скоро в RuStore» или «Готовится к запуску». После публикации можно подключить реальный URL.
5. **Реальные функции**: электрик, диагностика, пневматика/тормоза, автономные отопители, шиномонтаж, эвакуация, консультация по телефону, СТО-партнёры. СТО-партнёры — один логический раздел без дублей; нет рейсов, дальнемагистральной логистики, аптеки, химчистки, несуществующих сервисов.
6. **Карта**: Санкт-Петербург и Ленинградская область, реальная география, компактный виджет. На публичной странице допустимы придуманные метки **только при явной подписи** «Демонстрационная карта. Точки условные, данные не отображают доступность исполнителей». Никаких реальных персональных данных, ложных открытых заявок, рейтингов, активных мастеров и количеств как факта.
7. **Правило честной реализации**: если изображение — концепт, так и писать; настоящий браузерный скриншот показывать только после запуска кода. Код и дизайн должны максимально соответствовать согласованной картинке. Заказчик не согласовывал произвольную смену оформления.

## Различение трёх экранов
- Публичный ПК — маркетинговая главная, а не личный кабинет.
- Splash — только загрузка нативного приложения, а не отдельный маркетинговый экран.
- Публичный мобильный сайт — адаптивная веб-страница с входом и регистрацией.

## Ночная автоматическая сверка (запрошено владельцем 12.11.2026)
- **01:00 по Москве каждый день:** GitHub Actions `.github/workflows/ci.yml` проверяет типы, тесты, сборку, соответствие утверждённой айдентике и ночью запускает Playwright — реальные публичные скриншоты, офлайн-загрузку, пользовательские сценарии. Отчёты и screenshots — во вкладке Actions → «Проверка» → Artifacts.
- **01:40 по Москве каждый день:** GitHub Actions `.github/workflows/android.yml` собирает APK с локальными ресурсами, проверяет комплектацию и кладёт файл в Artifacts. Не отправлять APK в RuStore без отдельного ручного подтверждения.
- **Время не гарантировано до минуты:** GitHub ставит задания в очередь; фиксированное расписание использует UTC, Москва = UTC+3.
- Проверки не меняют утверждённые изображения, не редактируют код автоматически и не обещают исправить найденные баги самостоятельно. Ошибки останавливают workflow и видны в журнале GitHub. Не хранить ПДн и настоящие аккаунты в тестах.
- После push сохраняются облегчённые тесты для быстрого обнаружения сломанной сборки, тяжёлые браузерные сценарии — ночью или кнопкой `Run workflow`.
- Автоматическая проверка `scripts/verify-approved.mjs` запрещает заменять утверждённую фуру и карту, добавлять дубликаты элементов публичного входа и посторонние услуги. Перед выпуском требуется ещё визуальная ручная сверка реальных скриншотов.
