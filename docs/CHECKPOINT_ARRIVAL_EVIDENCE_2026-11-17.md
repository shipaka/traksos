# TrackSOS — КПП: серверная фиксация доказательств прибытия

Версия: 17.11.2026. Источники требований: #91, #92, #93, #94.
Ветка: feature/checkpoint-arrival-evidence-20261117.

**Статус:** изолированная backend-основа + PostgreSQL + тесты.
**НЕТ** публичного API/React UI, нет подключения к статусу заказа и платежам.
Это не GPS-навигация, не сертифицированная антифрод-экспертиза и не автоматический
договорный факт прибытия.

## Отдельный жизненный цикл КПП

1. Клиент/владелец активной заявки с уже назначенным исполнителем
   утверждает точку КПП, радиус 50–500 м, описание и необходимость пропуска.
   Заявка должна быть в состоянии accepted/en_route. Снимок неизменяемый;
   перенос КПП создаёт новый план/версию, не переписывает старую.
2. Если нужен пропуск, администратор ВРУЧНУЮ отмечает проверку разрешения.
   Обязателен защищённый reference к доказательству, SHA-256 и пояснение.
   Код НЕ обменивается паспортами или пропусками, НЕ проверяет ЭП и законность
   предоставления персональных документов. До реального документооборота
   этот статус нельзя использовать как законное основание передачи сведений.
3. Исполнитель только по своей назначенной активной заявке и после явного
   согласия на фиксацию GPS может создать idempotent arrival attempt.
   Один request_key/plan_id не создаёт вторую запись даже при повторах LTE;
   иной payload по тому же ключу вызывает конфликт.
4. Сервер собирает максимум 200 УЖЕ принятых реальных позиций из существующей
   performer_route_samples за последние 10 минут. Не принимает произвольный
   набор координат от клиента или исполнителя в API фиксации прибытия.
   Подделанное время устройства/прогноз не принимаются за GPS-подтверждение.
5. Чистый алгоритм проверяет два независимых GPS-наблюдения с интервалом
   15+ сек, последние 120 сек, accuracy <= 75 м, дистанцию + погрешность
   внутри согласованного радиуса и аномалии скорости. Изоляция профиля
   и роли обязательна. Один GPS point, длительный пропуск, spoof-flag,
   неточная/неизвестная позиция, нет пропуска — **needs_review**.
6. Даже хорошее GPS-попадание получает только **candidate**. Клиент или
   администратор может отдельно написать corroborated/insufficient с
   аргументированным описанием. Ни candidate, ни corroborated **НЕ** меняют
   status=arrived, не включают платный таймер, не формируют штраф или
   автокомиссию. Нужен отдельно утверждённый договорный механизм.
7. Клиент читает только результат и причины, без сырых точек геотрека.
   Исполнитель видит только свой заказ; чужие записи запрещены.
   Просмотр/проверки/удаление по сроку фиксируются в audit_log.

## Почему ни одно старое событие GPS не объявлено доказательством

На текущем main performer_route_samples хранит только lat/lng/received_at/
accepted. Там **нет** метаданных accuracy, location source, mock detection.
Миграция добавляет nullable accuracy_m, gps_source='unknown' и mock_location=false,
не меняя действующую отправку геопозиции.

Точки без этих достоверных полей в новом алгоритме попадают только в
**needs_review**. Это намеренно: старые координаты не доказывают прибытие
или прохождение КПП. В будущем точность должен передавать доверенный
адаптер GPS, с клиентским разрешением и серверной проверкой.

## Хранение и минимизация

Сырые 10-минутные снимки вынесены в отдельную таблицу
checkpoint_arrival_sample_snapshots, чтобы иметь возможность полного удаления
после истечения срока. Срок 30 суток — **черновой**, до юридической
проверки сроков, исключений по спорам, принципов хранения доказательств
и требований 152-ФЗ. Актуальные попытки, решения и SHA-256 остаются
неизменяемыми; отдельный admin-only метод purgeExpiredSnapshots удаляет
истёкшие GPS-снимки. Автоматического cron здесь пока нет.

Для законной защиты доказательств при открытом споре потребуются
договорные сроки, правила legal hold, отзыв доступа и политика удаления
источника performer_route_samples. До этого НЕ включать долгосрочную
сборку GPS на production. Фонового слежения и dead reckoning нет.

## Файлы

- server/src/services/checkpointEvidenceCore.ts — доказательная проверка.
- server/src/services/checkpointEvidence.ts — роль, хранение, consent, версии,
  повторные запросы, ручной разбор, приватность и отчёт по конкретной заявке.
- server/migrations/210_checkpoint_arrival_evidence.sql — изолированные
  PostgreSQL-таблицы и ограничения.
- server/test/checkpointEvidence.test.ts — unit + реальная test PostgreSQL
  через обычные фикстуры сервера, роли, cash-only заказ, CSV/банка нет.

- PostgreSQL schema migration на disposable DB и CI перед merge.
