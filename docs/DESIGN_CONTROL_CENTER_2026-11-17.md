# TrakSOS · Дизайн-контроль / единый процесс согласования
**Актуальная задача управления:** [Design Control Center #126](https://github.com/shipaka/traksos/issues/126).  
**Прототипы и дизайн:** [draft PR #121](https://github.com/shipaka/traksos/pull/121).  
**Функциональная экосистема:** [draft PR #111](https://github.com/shipaka/traksos/pull/111).  
**Статус:** рабочее правило управления дизайном. Не менять production/main по одному только решению из этого файла.

## Источник правды
1. **Реальный функциональный контракт** — актуальный серверный код/миграции/API/проверка доступа по соответствующим PR, а не старые скриншоты, демо-кнопки или формулировки ассистента.
2. **Решения владельца** — комментарии в #126, где указаны D-ID, вариант, версия и правки. Решения внутри чата переносятся сюда после подтверждения, не теряются между беседами.
3. **Дизайн-артефакт** — один зафиксированный для каждого пакета HTML/CSS+assets с версиями и реальными скриншотами, а не AI-картинка. Каждой кнопке соответствует действие/доступность/empty/error state.
4. **Дизайн-готов** ≠ **код интегрирован** ≠ **проверен Android** ≠ **готов к продакшену**.

## Не конфликтовать с программированием
- Ветку `design/future-proof-role-workspaces-20261117` и PR #121 использовать только для `design/`, `docs/` и изолированного визуального прототипа.
- На функциональных ветках не перезаписывать бренд, CSS, дизайн-ассеты и навигацию ради новой функции без отметки конфликта с D-ID.
- После утверждения дизайна создавать отдельный интеграционный PR от **актуального** SHA функциональной базы, отбирать изменения по файлам и запускать тесты ролей, маршрутов, API, скриншотов/адаптивности.
- ЗАПРЕЩЕНО смешивать feature #111, design #121, другие незавершённые ветки и `main` без проверки пересекающихся файлов, CI и приёмки владельца. Пользователь не должен получать непроверенные ветки как готовый APK.
- Для будущих функций/ролей используется конфиг маршрутов и `ModuleRegistry` с доступностью `available/closed/unauthorized/region-restricted/draft`, реальный серверный ACL обязателен.

## Продуктовый и визуальный приоритет
- **Клиент, владелец, водитель** — главная аудитория. При наличии водительской роли — «Эфир» заметен на первом экране рядом с SOS.
- Одна учётная запись может включать несколько разрешённых ролей; отображение не создаёт полномочия.
- Карточка **«Специалист по ЭБУ»** на клиентской главной, в каталоге и соответствующей анкете; в SOS остаются **три основных направления: мастер/эвакуатор/СТО**, ЭБУ — внутренняя специализация мастера.
- ПК и Android не копии: ПК — рабочие колонки/детали/история; Android — одно главное действие, короткие блоки, вкладки/один следующий этап, доступность пальцем, плавная отдача.
- Фотография помогает понять сервис до чтения, но каждый ассет имеет права, точное назначение, responsive crop и локальный fallback.
- Федеральный бренд ≠ автоматический федеральный SOS/магазин; не показывать ложные цены, остатки, счётчики или запущенные будущие функции.

## Жизненный цикл каждого блока
`TECH-READY → 3-VARIANTS → OWNER-SELECTED → HTML-REFERENCE → DESIGN-APPROVED → INTEGRATION-PR → BROWSER-VERIFIED → ANDROID-VERIFIED → RELEASE-CANDIDATE`

- **TECH-READY:** проверка актуальных backend/ACL и сценариев.
- **3-VARIANTS:** 3 действительно разные композиции A/B/C, у каждого ПК+Android + описание преимуществ/рисков. Предпочтение исполнителя обязательно.
- **OWNER-SELECTED:** пользователь выбрал A/B/C и поправки; записать ссылку на комментарий #126. Молчание не согласие.
- **HTML-REFERENCE:** настоящий интерактивный браузерный макет, совпадающий с предлагаемыми визуальными ассетами.
- **DESIGN-APPROVED:** пользователь посмотрел эталон, после этого заморозить фото/композицию/тексты/поведение в версии, изменение — новый запрос.
- **INTEGRATION-PR:** встроить в реальные React/Android-сценарии, НЕ в production.
- **BROWSER/ANDROID-VERIFIED:** сравнивать точные скриншоты и тестировать активную навигацию, критические ошибки/role ACL. Android только на реальном APK/устройстве.
- **RELEASE-CANDIDATE:** владелец отдельно разрешил тестовый/боевой деплой после релизных ворот.

## Единый пакет материалов для проверки владельцем
- 3 варианта с понятными отличиями (не 3 почти одинаковые картинки).
- Ссылки на визуальное сравнение ПК 1440×900 и Android 390×844; дополнительно контроль 320,360,768.
- Рабочий HTML/стенд с кликами, анимациями, пустыми/ошибочными состояниями; список **что кликается**, **что фиктивно**, **что ещё нет на сервере**.
- Пошаговая видеоэкскурсия **по всему экрану/разделам**, а не только одной заявке.
- Ведомость точности: `component id → route/action → ACL → data/API → asset filename/license → mobile/desktop screenshot → result`.
- 1–3 конкретных вопроса на утверждение, после которых можно идти дальше.
- Критические нарушения всегда блокируют приёмку: неверный доступ, утеря данных, ложный платёж/заказ/ETA, несуществующее покрытие, отличия от утверждённых экранов без разрешения.

## Формат «почти реального времени»
- В чате согласовываем варианты и сразу принимаем решения; после каждого завершённого блока обновляем #126 / PR #121 и присылаем ссылку.
- GitHub показывает фактические commits/PR/CI и комментарии, но **ChatGPT не вносит изменения самостоятельно между сообщениями**. Ни один обещанный макет не считается созданным до фактического файла/снимка/ссылки.
- Временная web-preview ссылка возможна только если настроен проверенный staging/preview-хостинг и подключен CI; не считать blob на GitHub полноценным живым URL.
