# TrakSOS — единая дизайн-основа кабинетов с запасом на развитие
**Дата решения:** 17.11.2026 · **Статус:** согласованная композиционная концепция + технический проект интерфейсов; не означает готового UI или релиза.  
**Репозиторий:** shipaka/traksos · **Назначение:** design-only контракт для web, mobile web и Android WebView.

## 0. Приоритеты и неизменяемое
- Утверждённый публичный эталон остаётся в `docs/TRACKSOS_DESIGN_CANON_2026-11-14.md`. Не заменять hero, шесть сервисных плиток, логотип/палитру без отдельного согласования.
- Владелец выбрал **структуру варианта 3 (премиальный рабочий командный центр) + профессиональную среду варианта 2 (дорога/мастерская/офис) + умеренный кинематографичный свет и переходы**. Это направление для *внутренних кабинетов*, не разрешение перерисовывать главную.
- Принцип: сначала действия и данные, затем визуальная иерархия, затем фотографии, освещение, анимация. Не добавлять на фото лишние услуги, кнопки, счётчики или выдуманные заказы.
- **Не путать уровни готовности:** предусмотрено в сетке / есть маршрут в draft PR / объединено в main / принято в Chromium+APK / проверено на VPS / разрешено к публикации. Наличие красивой картинки ≠ работающая функция.
- Сопутствующая разработка: draft PR #112 (слой кино-графики над PR #108), draft PR #111 (Эфир, Клуб, ТехБаза, партнёрство, курьер/склад/магазин). Не менять их файлы из этого пакета; интеграцию выполнять только после анализа актуальных SHA и конфликтов.
- Не открывать магазин, онлайн-деньги или федеральную тарификацию SOS ради оформления. Не показывать «живые» точки, ETA, цену, рейтинг и исполнителей без подтверждённого источника.

## 1. Принцип архитектуры — одна оболочка, разные роли
Рекомендуемые будущие компоненты (проект для реализации, пока **не подключены кодом**):
- `WorkspaceShell`: общий каркас, логотип, переключатель **доступных** ролей, breadcrumbs/возврат, уведомления, профиль/выход, безопасные отступы, доступность.
- `RoleNavigation`: конфигурация маршрутов и приоритетов на роль + отдельная мобильная нижняя панель; server ACL остаётся источником истины, визуальный feature flag не заменяет разрешения.
- `RoleHero`: компактная полоска профессии с локальной реальной фотографией, без закрытия содержимого, и один основной рабочий вызов.
- `ActionPanel`, `TaskQueue`, `StatusTimeline`, `VehicleCard`, `MoneySummary`, `DocumentCard`, `ContextNotice`, `EmptyState`, `ErrorState`.
- `FeatureSlot`: слот для будущей функции по состояниям `disabled / preparation / available / unavailable-region / unauthorized`; в production скрывать или давать честное объяснение, **не изображать активность**.
- `RoleTheme`: только фотосцена, мягкие акценты и служебная иконография меняются; поведение, кнопки, размеры, типографика, паттерны статусов едины.
- `ContextAction`: дополнительное действие появляется **в контексте** заявки/товара/машины/рейса. Не засорять главную роль чужими сценариями.

### Базовая компоновка
**ПК 1440:** боковая рабочая навигация → компактный header → полоска роли (умеренный cinematic hero) → главная задача/активная очередь → контекстные сервисы → история/вторичные инструменты. На странице минимум один очевидный главный CTA, без фиктивных KPI. При узком ПК сворачивать sidebar.  
**Телефон 320/360/390:** короткий header; сверху приоритетное действие; сразу видимый текущий заказ/рейс/состояние; ниже максимум 2×2 быстрых плиток; второстепенные разделы в «Меню» или профиль. **Нижняя панель до 4 ключевых разделов** (по роли), без двух конкурирующих способов SOS. Фотополоса на телефоне не должна выталкивать рабочий контент за первый экран.  
**Планшет 768:** гибрид: рабочая колонка + второй контекстный блок, без дублирования бокового/нижнего меню.  
**Android:** те же разделы, но корректный safe area, жест «назад», системная клавиатура, уведомления, биометрия/PIN из #108 после отдельной приёмки. WebView не должен ощущаться неадаптированным сайтом.

### UI-состояния обязательно для каждого экрана
Загрузка; нет данных; нет доступа; временно недоступно; нет интернета; ошибка с повтором; активное действие; успешное завершение; конфликт/повторная отправка. В пустом состоянии — честное объяснение и полезное действие, не фиктивная статистика.

## 2. Матрица первой страницы и навигации
Предложенная схема (требует реализации/проверки, не означает изменённый действующий UI):

| Рабочая роль | Сначала на главной | Контекст / второй уровень | Мобильная нижняя навигация (проект) |
|---|---|---|---|
| Клиент / владелец | SOS; открытая заявка; мастер/эвакуатор/СТО/консультация | транспорт и история, страхование, техосмотр, запчасти (закрыто до разрешения), поддержка, финансы | Главная · Заявки · Транспорт · Меню |
| Водитель | SOS; привязанный грузовик; активная заявка; бесплатный Эфир | чат заявки, дорожные события, консультация, разрешения владельца, история | Главная · Эфир · Заявки · Меню |
| Мастер | статус «на линии»; новая/текущая заявка; **один доступный следующий этап** | профиль, специализации, финансы, рейтинг, партнёрский уровень, закрытая ТехБаза, профклубы | Линия · Заявки · Финансы · Меню |
| Эвакуатор | статус; новые вызовы; техника и соответствие заявке; текущий рейс/статус | история, выплаты, график, профиль, партнёрство | Линия · Заявки · Финансы · Меню |
| СТО | новая запись; очередь; активные работы; доступность постов (только если подтверждена) | карточки ТС, ремонты, документы, финансы, ТехБаза, профессиональный клуб | Обзор · Записи · Работы · Меню |
| Страховой агент / техосмотр | очереди назначенных заявок, требующих действия; явные переключатели Страхование/Техосмотры | документы, предложения, статусы, две независимые финансовые ведомости, настройки | Страхование · Техосмотр · Финансы · Меню |
| Администратор | требующие внимания очереди, доступность, спорные случаи, системное здоровье (только реальные сигналы) | полные тестовые кабинеты тех же ролей, назначение прав, склад/курьеры, платежи/возвраты, модерация, отчёты | Обзор · Очереди · Роли · Меню |
| Модератор | жалобы, обращения, проверки, подозрительные сообщения | профессиональный контент/права, апелляции; **без финансов и тарифов администратора** | Очереди · Обращения · Проверки · Меню |
| **Курьер — отдельная роль** | один активный рейс, его стадия, следующая допустимая операция, текущий адрес или склад | проверка посылок, маршруты только своих рейсов, подтверждение вручения/неудачи, возврат, GPS-согласие, история | Рейс · Посылки · История · Меню |
| Склад / диспетчер | очередь комплектации; расхождения; выдача; возвраты | сверка артикулов, количества, упаковки, причины исключений, журнал | Комплектация · Расхождения · Передача · Меню |

**Разграничение:** склад/диспетчер на текущем этапе — защищённые административные экраны из #111, а не автоматически новый публичный тип регистрации. Курьерскую роль назначает только администратор. Курьер ≠ водитель автопарка ≠ мастер ≠ будущий перевозчик «Грузов».

## 3. Курьерский сценарий, который нельзя переделывать потом
Источник функционального контракта: PR #111, `web/src/screens/courier.tsx`, `courierAdmin.tsx`, `courierWarehouse.tsx`, `courierTracking.tsx` и `docs/SHOP_COURIER_LAST_MILE_AND_PRICE_2026-11-16.md`.

### Кабинет курьера — всегда одно ведущее действие
1. **Нет рейса:** «Пока нет назначенных рейсов», обновить, профиль; не рисовать искусственный маршрут.
2. **Назначен:** сведения о складе, список посылок, кнопка «Принять рейс».
3. **Принят / сборка:** список конкретных заказов и проверка фактического забора; нельзя начать доставку до завершения всех обязательных приёмок.
4. **Доставка:** *только текущая остановка* и её действия: открыть внешний навигатор, подтвердить прибытие, вручение с участием получателя, либо зафиксировать неудачу с причиной. Нельзя пролистывать и менять статусы чужих остановок.
5. **Возврат:** понятная карточка склада и перечень невручённых посылок, без кнопки «возврат денег» или фиктивного завершения складского возврата. Физический возврат подтверждает уполномоченный сотрудник.
6. **Завершён:** короткая сводка и история, никаких открытых кнопок активного рейса.

**Приватность:** адрес клиента и данные получателя отображаются только в разрешённом окне и только по нужной остановке; после завершения/смены скрываются. Закупочные/розничные цены курьеру не показывать. GPS отдельно включается по согласию, не автоматически; точка только активному получателю, сбрасывается по завершении/смене/отзыве. Не выдавать приблизительную линию на декоративной карте за настоящий маршрут и ETA. Не давать водителю взаимодействовать с приложением за рулём: крупные цели касания, безопасные состояния, работа со стоянки.

### Склад и диспетчер — своя рабочая сетка
Обзор задач → фактическая проверка **артикул + количество + упаковка** → расхождения и повторная сверка → подтверждённая выдача курьеру → мониторинг только своих разрешённых рейсов → физический возврат → аудит и отчёты. На ПК — две колонки «очередь слева / детали справа»; на телефоне — сначала список, затем карточка без горизонтальных таблиц. Сканирование не имитировать, если аппаратный сканер/камера не настроены. Складское расхождение блокирует отправку; визуальный сигнал связан с реальным серверным статусом.

## 4. ТехБаза, Эфир, Клуб — предусмотреть с первого дня
**ТехБаза мастера/СТО:** поиск по марке/модели/году/системе/коду ошибки → результат → карточка → применимость/источник/права → профессиональное обсуждение → предложение материала на двухэтапное ревью. Из заказа «Энциклопедия» или «Спросить коллег» с явным подтверждением текста без ПДн клиента. Не создавать красивых несуществующих схем, не показывать клиенту закрытую базу. Дизайн документов отличается по плотности, но использует ту же оболочку и типографику.  
**Эфир водителя:** messenger-first, быстрый список комнат и диалог; на мобильном экран переписки без большого hero, поле ввода поверх клавиатуры; маршруты/города по добровольной подписке, без публикации GPS; личные чаты по согласию; сеть/офлайн/обновление. Дорожные сведения от пользователей с пометкой неподтверждённости и сроком актуальности.  
**Клубы профессионалов:** карточка случая (модель/система/симптом) + переписка + разрешённые вложения и статус решения. Доступ только допущенным ролям и специализациям.  
**Партнёр:** отдельный рабочий раздел «Мой уровень» (Старт/Активный/Приоритетный), показатели с малой выборкой, разъяснения, апелляции и решения администратора. Не подменять этим «Новичок/Проверенный/Лучший» и не менять комиссию автоматически.

## 5. Будущие направления — архитектурный резерв, а не меню с пустыми кнопками
- «TrakSOS Грузы»: будущий собственный workspace для отправителя, перевозчика и диспетчера; система разделов «Заявки / Грузы / Маршруты / Документы / Финансы». **Пока не создавать реальные маршруты, публичные вкладки или фальшивые предложения**.
- «Водители и работа»: будущий workspace с вакансиями, откликами, профилем и проверкой работодателя; не смешивать с водительским «Эфиром» и персональными данными.
- Корпоративный пакет: развивать существующий «Мой парк» до многопользовательского управления по правам, с расходами/ограничениями/историей, без нового дизайна оболочки.
- Поставщики/пункты выдачи/партнёрская сеть: будущие дополнительные роли и операции; наследуют shell, task queue, document card, money summary и разграничение прав.
- Новые AI/аналитические функции — **только отдельные контекстные модули**, не постоянный чат-бот поверх рабочего экрана. Показывать источники и степень достоверности.

Для каждого будущего направления резервируем **маршрутную область/компонентный слот**, но не видимый пустой раздел. Активировать только после согласования продукта, backend, прав, экономики и тестов.

## 6. Кинематографичность, совместимая с настоящей работой
- Фото и атмосферный свет только там, где помогают ориентироваться в роли: водителю дорога, мастеру ремонт, эвакуатору тяжёлая техника, СТО ремзона, курьеру реальная доставка/склад, администратору лаконичная командная карта (без фиктивных точек).
- Локальные оптимизированные WebP/AVIF с проверенными правами; резервный градиент при медленной сети, слое загрузки и reduce-data.
- Длительная анимация **не нужна**: 150–300 мс смена состояния/вкладки, мягкое появление заголовка, тактильная обратная связь при событии; никаких autoplay-видео, постоянного 3D и дергающихся цифр в финансовых действиях.
- Дизайн-токены для основного контента: фон navy/graphite, cyan primary action, magenta для тщательно выбранного вторичного акцента, остальные системные статусы имеют текст и пиктограмму (цвета недостаточно). Не делать всё фиолетовым или всё розовым.
- Контраст и читаемость выше декора; не перекрывать фото текстом без сплошного градиента; реальные изображения грузовиков без искажений/обрезанной техники; не создавать «квадратные машины» из SVG вместо фотографий.
- Отступы/плотность: минимальная зона касания 44×44 CSS px (на мобильном предпочтительно 48), footer над Android navigation safe area, кнопки не уходят под клавиатуру, не прячем «Назад/Выйти/Смена пароля».

## 7. Единый набор необходимых UX/функциональных тестов
- Разрешения: авторизованный клиент не видит курьерские/складские/ТехБаза-материалы; куратор/админ видит свои очереди; роль недоступна по прямому URL.
- Режим админской песочницы — **реальный полный кабинет** той же версии, с отдельной тестовой базой и явной кнопкой «Назад в админку», без подмены однострочным тренажёром.
- Мобильные скриншоты реального Chromium **320, 360, 390**, планшет **768**, ПК **1440**; затем *физический* Android APK; отдельная проверка темной системной панели, жеста «Назад», PIN/биометрии и push.
- Честные пустые/ошибочные/недоступные/региональные состояния, без зависших заглушек; отсутствие горизонтальной прокрутки, фокус-клавиатуры и невидимых кнопок; long-text RU.
- Для курьера: текущая остановка, запрет чужих адресов, отмена/неудачная доставка/возврат на склад/повторный рейс, GPS consent, background/foreground. Визуальная готовность ≠ юридическая или банковская приёмка.
- Для Эфира/ТехБазы: слабая сеть, reconnect, тяжёлая история, многословные сообщения, права на документы, права ролей, возврат из модалки.
- Для магазина: СПб-only до отдельного расширения, сообщения «Пока недоступен в вашем регионе», закрытый переключатель до разрешения владельца.
- Не менять файловый контур #111/#112/#108 без ребейза и сравнения изменений; визуальную приёмку проводить только со скриншотами реально собранного кода, не с ИИ-макетами.

## 8. Порядок интеграции, не блокирующий соседние ветки
**Этап A (этот документ):** зафиксировать будущую компоновку и матрицу без изменений боевого приложения.  
**Этап B:** на актуальном SHA интегрировать базовые `WorkspaceShell / RoleNavigation / RoleHero / FeatureSlot` с существующими экранами; сохранить утверждённый guest canon; тесты всех основных ролей.  
**Этап C:** адаптировать PR #111: courier / warehouse / TechBase / Air / Clubs / Partner; отдельно проверить mobile-first и реальные роли.  
**Этап D:** для будущих направлений добавлять новые workspace-конфигурации без переделки оболочки; включать только за независимыми server-authorized feature gates.  
**Этап E:** сравнить скриншоты 390/1440 с утверждённым эталоном и согласованным гибридом 3+2, проверить действия и нагрузку, только после этого предлагать merge/deploy.

**Критерий успеха:** при появлении новой роли мы добавляем конфигурацию, операции и тематический визуальный слой, а не переписываем весь сайт, Android-навигацию, систему компонентов и дизайн заново.
