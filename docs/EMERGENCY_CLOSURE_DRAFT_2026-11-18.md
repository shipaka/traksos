# Аварийное завершение при потере связи — черновая реализация

**Дата:** 18 ноября 2026. **Ветка/PR:** feature/unilateral-close-offline-20261118 / #175. **Статус:** DRAFT; не сливать в main и не публиковать без зелёного CI и приёмки финансов/доступов.

**Внешние заявки за вознаграждение (#174) на паузе** по прямому требованию владельца. Эта ветка не включает гостевые формы, лиды, выплату за рекомендации или налоговую схему.

## Что код уже делает
1. Только назначенный мастер/эвакуатор после \`awaiting_confirmation\`, зафиксированного результата и суммы может POST \`/api/orders/:id/emergency-close\` с причиной, пояснением и идемпотентным ключом. Сохранение записи и сообщений/уведомлений атомарно; повторение не создаёт второй случай.
2. Физическая занятость исполнителя отделяется от денег: \`orders.status=awaiting_confirmation\`, \`unilateral_status=pending_client\`. Ожидание ответа не блокирует новые выезды, **если нет другой активной работы**. Все известные проверки занятости в \`OrdersService\` и \`AuctionService\` согласованы. Подтверждение старой заявки не сбрасывает \`on_job\` более новой работы.
3. Клиент видит точную версию предложенной суммы и отвечает через штатный защищённый \`/confirm\` либо через \`/emergency-dispute\`. Согласие записывается в отдельную строку; оплата идёт только через существующие проверки и платёжный журнал. Возражение **не** возвращает заявку в \`working\` и открывает дело модерации. Если дело уже было создано по просрочке, туда добавляется возражение без дубля.
4. Нельзя править строки расчёта во время аварийного подтверждения, отменять такую заявку обычным путём или пользоваться старым маршрутом спора/неоплаты. Защита суммы есть также в PostgreSQL, не только в интерфейсе.
5. Серверный таймер \`app.unilateral.tickSla()\` запускается при старте и каждую минуту: по умолчанию напоминание через **24 часа**, передача на ручной контроль через **72 часа** после аварийной сдачи. **Это настраиваемые технические значения для пилотной проверки, не утверждённые окончательные сроки оферты.** При разбирательстве, согласии или смене статуса новые напоминания прекращаются. Все события с блокировками строк, журналом, системным чатом и долговечными уведомлениями в БД.
6. Молчание НЕ означает согласие. Срабатывание SLA не списывает/не распределяет деньги, не изменяет \`completed_at\` или \`amount_confirmed_at\`, не изменяет банковскую авторизацию. Состояние банковского \`hold\` зависит от реального провайдера; при отсутствии/истечении авторизации нельзя обещать «деньги заморожены».
7. Клиент и мастер видят правильный статус в веб-карточке, списках; активные физические работы отделены от «Работа сдана · ждём ответа». Основные кнопки мастера перенесены ближе к обзорному статусу.

## Проверки PR
- Unit: идемпотентность, отсутствие преждевременной оплаты, ACL, несогласие.
- PostgreSQL API integration: реальный \`client→master→amount→emergency\`, согласие, отказ, один спор, напоминание ровно один раз, одна эскалация, ответ после эскалации, сохранение \`awaiting_confirmation\`.
- Регрессия: новый выезд исполнителя после аварийного освобождения и позднее подтверждение старого расчёта НЕ переводят его обратно «на линию» во время нового выезда.
- CI: backend types/tests, frontend build, browser routes, load (200), Android smoke. Статус определяет только последняя завершённая проверка конкретного SHA.
