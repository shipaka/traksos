Прежде чем объединять, проверять миграции и обратную совместимость на изолированной БД.

### Особая проверка миграций

В одном PR находятся **два разных** файла с порядковым префиксом `146`: `146_ecu_specialist_linked_orders.sql` и `146_shop_trace_supplier_allocations.sql`. Текущий мигратор применяет миграции по **лексикографически отсортированным именам файлов**, записывая *полное имя* в `schema_migrations`. Это не автоматически дубликат в БД, но пересечение нумерации требует проверки зависимостей и линейной истории релизов: при переносе только одного модуля порядок может измениться. Не переименовывать уже применённые миграции без стратегии совместимости.

### Критерии для каждого под-PR

- **Функциональный** PR (с кодом/тестами), а не только документация и красивые мокапы.
- Указывать SHA исходного фрагмента #111, SHA главной ветки, список изменённых файлов и зависимости.
- Финансовые функции остаются в mock/closed до юридической и банковской приёмки.
- Не добавлять реальные логины, SMS, push, платежи, геоданные в тесты. Для нагрузочного теста — disposable Postgres.
- Сначала узкие тесты модуля. После каждого законченного интеграционного пакета, **не после каждой правки**, один полный E2E + 1000 участников/курьеров. Действующий `main` не испытывать 1000 участниками.
- Отдельная приёмка React/Android и согласованного дизайна из #126.
- Признак завершения: PR merged → образ GHCR по SHA → sandbox check → фактическая выкладка на sandbox → пользователь проверил → только затем продакшен с разрешением.

## Стартовая очередь без пересечения общих файлов

1. **Параллельно:** техаудит миграций и ограничений `#111`, дизайн-прототипы `#121`, sandbox deploy `#133`.
2. **Затем:** выделить сервис ЭБУ отдельными файловыми операциями без замены `app.ts`.
3. **После интеграционного окна:** маленький PR только на подключение маршрутов ЭБУ и UX, затем отдельно Эфир.
4. **Курьерскую логику** можно разрабатывать параллельно с ТехБазой в изолированных файлах, но не сливать прежде сквозных проверок ACL/схемы/цен.
