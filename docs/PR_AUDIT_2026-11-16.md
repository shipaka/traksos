# TrakSOS — ревизия всех старых PR и перенос в единый релиз

Дата: 16 ноября 2026. Рабочая задача [#107](https://github.com/shipaka/traksos/issues/107). **Статус документа — интеграционная ветка #105, НЕ рабочий VPS.**

## Разделение статусов

- **Архивный PR закрыт без merge** — исторический diff доступен, требования перенесены в #107, но это не утверждение, что каждое поведение проверено на Timeweb.
- **Есть в main** — исходный файл/миграция/код реализованы и попали в основную ветку; это НЕ гарантия работы реальных банков/SMS/телефонии.
- **Проверено CI** — только для точного SHA проверенного прогона; после изменения даже одной строки требуется повторная проверка.
- **Готово к запуску** — отдельный результат диагностики, резервных копий, пробного восстановления, живых сценариев и юридических/аппаратных гейтов.

## 2. Финансово-гарантийные PR — почему можно архивировать старую лестницу

В старой цепочке #44 → #46 → #48 → #53 → #57 → #60 → #64 → #66 → #67 → #68 → #69 → #70 вместе с вспомогательными #45/#54/#56/#62/#63:
- **Все затронутые пути присутствуют в `main`**. Миграции `097–107`, `110`, база нагрузочного теста и многие исходные модули имеют **точно такие же SHA blob**, как в верхней ветке #70.
- `server/src/payments/service.ts`, `server/src/services/admin.ts`, `server/src/services/warrantyRecourse.ts` и некоторые другие файлы **различаются**: текущий `main` содержит иные/более поздние правки. Насильственное слияние старых черновиков могло их откатить. **Без новой финансовой интеграции старую цепочку закрываем как superseded/архив, не как «денежный релиз готов»**.
- Ключевые сценарии остаются **обязательными к проверке отдельно**: нет второго банковского capture/refund при потере ответа, долговечные intent и idempotency, фактическая выплата по реквизитам только после подтверждения администратором, согласованные 0/25/50/100% с доказуемыми GPS-порогами, юридически обоснованные рекламации и компенсации исполнителя без незаконных штрафов.
- До настоящей приёмки с ЮKassa и юристом `PAYMENT_PROVIDER=mock` и магазин `enabled=false`. Нагрузка 200 виртуальных аккаунтов **не заменяет тестов реального банка**.

## 3. Актуальный крупный кандидат #105

58/58 согласованных файлов старой sandbox-ветки #89 перенесены поверх уже утверждённого `main` (в отличие от старых демо копий). В эту же ветку дополнительно перенесены:
1. Проверка безопасного одноразового входа из #100.
2. Отдельная шапка тестового режима без гостевой регистрации из #86.
3. Переименование ложного «Расширенного поиска» в реальные «Настройки заявок» из #39.
4. Исправление мобильной плашки «ТЕСТОВЫЙ РЕЖИМ» (глобальный стиль скрывал общий класс `.pill.accent`).

**Важная эксплуатационная зависимость:** `deploy/update-site.sh` в #105 становится fail-closed и требует заранее развернутую и проверенную изолированную sandbox на другом домене, БД и сетях. Это означает: **нельзя просто нажать «обновить» вечером на старом VPS без подготовки**, даже после зелёного CI. Не обходить это удалением проверки. Собрать один immutable Docker SHA, сохранить backup и проверить оба контура.

Миграции 112/113 в интеграционной ветке добавляют новые имена рядом с уже существующими 112/113 из main. SQL мигратор хранит **полное имя файла**, а не один номер, поэтому одинаковые числовые префиксы сами по себе не означают конфликт. Реальную миграцию действующей БД выполнить только с сохранённым backup.

## 4. Неподтверждённые функции — источник ещё не равно готовность

- Реальное развертывание Timeweb и SMS.ru/Т-Мобайл, админский вход с физического телефона, RuStore Push на заблокированном устройстве.
- Страховые корпоративные/лизинговые продукты по договору/через Pampadu; самозанятый брокер, комиссии, реальные оферты.
- Поставщик Автоконтинент, юридически разрешённый VIN-каталог и проверенные аналоги, подмена телефонных номеров и запись разговоров.
- Роли/сценарии всех кабинетов, лицензии на карту/навигатор, сложные GPS/КПП, договоры/152-ФЗ, резервное восстановление.
- Возвраты и расчёты денег только после отдельных банковских/юридических испытаний.

## 5. Что делать, чтобы выйти на единое обновление

1. `main` и PR #105 сверять по SHA; все CI, Android, Docker, load и реальные скриншоты — **для одной и той же ревизии**.
2. После зелёного #105 — сравнить изменения с новым `main`, проверить изоляцию, права, сценарий admin→sandbox и список оставшегося. Только затем объединение.
3. На Timeweb сначала diagnostics, backup, пробное восстановление, отдельная sandbox и фейковые внешние провайдеры; затем обновлять prod одной сборкой без трогания БД/магазина вручную.
4. По #107 вести фактическую приёмку; старые PR закрываются с пояснением, что их **история сохранена**. Вопрос «работает ли у клиента» закрывать только реальным smoke на обновлённом сервере.
