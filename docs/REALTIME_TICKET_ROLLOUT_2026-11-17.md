# TrackSOS WebSocket: поэтапный переход на одноразовые пропуска

Релизный риск: [#115](https://github.com/shipaka/traksos/issues/115). Источник реализации: draft PR #111; перенос — изолированный PR, а не merge всей экосистемы.

## Этап 1 — безопасная совместимость (этот PR)

- Сервер выдаёт 32 криптографически случайных байта как base64url-пропуск через `POST /api/auth/realtime-ticket` с обычным заголовком авторизации.
- В PostgreSQL хранится **только SHA-256 пропуска**, привязка к пользователю и исходной сессии, TTL 30 секунд.
- SQL `DELETE ... RETURNING` делает пропуск одноразовым даже при двух одновременных подключениях. У ограничителя — до пяти ожидающих пропусков на сессию.
- Новый web/Android WebView идёт на `/ws?ticket=...`; постоянный ключ входа не попадает в URL. Неудачная выдача пропуска **не** переключается автоматически на `?token=`.
- Gateway перепроверяет действующую сессию и текущие роли каждые 30 секунд (интервал в тесте уменьшен); при выходе, блокировке и отзыве роли закрывает уже подключённую сессию.
- **Только для совместимости** ранее установленных APK сервер временно принимает `/ws?token=...`. Поддержка старых клиентов — не доказательство устранения всей утечки. Очистка просроченных пропусков идёт в обычной housekeeping.
- Конфигурация маршрутизации/доступов VPS, SMS, банк, торговля, деньги и дизайн не меняются.

Миграция main: `116_realtime_one_time_tickets.sql`, её не переименовывать после применения. Черновик #111 использует другую позицию `131_realtime_one_time_tickets.sql` с идемпотентной схемой. При извлечении #111 не переносить второй SQL-файл автоматически: согласовать линейную историю миграций с интеграционным владельцем (#135).

## Этап 2 — снятие legacy, только после проверки установленной базы APK

1. Сначала выкатить сервер **в песочницу**, проверить миграцию, живую авторизацию, WebSocket 200, ticket reuse/TTL, logout, роли, reconnect, offline LTE, Android API 29/35 и физический Android.
2. Проверить HTTP access-логи Caddy/reverse proxy: нельзя хранить query token в логах. Метрику доли legacy-клиентов собирать **только агрегированно**, без IP, номера телефона, user ID, самого токена или полного URL.
3. Обновить все поддерживаемые APK и web через подтверждённый канал распространения; не считать, что каждый пользователь уже обновился при merge в GitHub.
4. После доказанного перехода **отдельным PR** запретить query `?token=` на WebSocket upgrade и добавить регрессионный тест отказа. До этого #115 остаётся **открытым**.
5. Только после приёмки владельцем и согласованного релизного окна обновлять production. Это изменение само по себе ничего не выкладывает на VPS.

Финальный нагрузочный тест на 1000 смешанных ролей — в общем интеграционном пакете, не на production.
