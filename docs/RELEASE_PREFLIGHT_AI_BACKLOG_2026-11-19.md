## 3. ИИ: что реально готово и что надо реализовать

### Факт
В черновом PR #111 у ТраксБота есть **только демонстрационные диалоги** и настройки личного тона `straight/humor/road`. Нет внешнего провайдера, надёжного inference API, безопасной передачи контекста, retrieval по проверенным источникам, нагрузочных испытаний модели и production эксплуатации. Не маркировать предпросмотр как действующего ассистента.

### AI-0: договор интерфейса и ограничения (до разработки модели)
- Вход в ИИ по явному вызову, в разрешённой роли/чате. Серверная проверка ACL на каждом обращении, отдельные лимиты, бюджет и журнал технических событий без содержимого личных переписок по умолчанию.
- Отдельное явное согласие на передачу **выбранного** фрагмента обращения провайдеру. Без адреса, номера телефона, VIN, GPS, чужих чатов или финансов по умолчанию. Отзыв согласия, политика хранения и удаления.
- Бот не закрывает, не оплачивает, не назначает, не передаёт заявку автоматически. Все действия через обычные API с отдельным подтверждением пользователя.
- Опасные ситуации (тормоза/EBS, возгорание, ДТП, утечки, травмы) → безопасное сообщение без юмора, совет прекратить опасные работы и обратиться за экстренной/профильной помощью, не «диагноз по фантазии».

### AI-1: реальный ТраксБот — отдельный малый PR
- Серверный adapter для выбранного LLM-провайдера; секреты **только** в защищённом окружении, флаг `AI_ASSISTANT_ENABLED=false` до запуска, таймауты, budget/cost caps, circuit breaker, безопасная деградация, retry без дублирования запросов.
- POST + получение ответа только от авторизованного пользователя, честная маркировка «ИИ · ТраксБот», трассировка request ID, rate limiting, quotas. Три тона не должны менять безопасность.
- Тесты: нет согласия/нет роли/чужой чат; injection и попытка получить персональные данные; истёкший токен; 429/timeout/502; идемпотентные повторы, отключённая модель; плохая сеть, ответы без выдумывания доступных исполнителей.
- Android 29/35, слабая сеть, 390/1440, контекст «не отправлено/не удалось», без блокировки SOS и других кабинетов.

### AI-2: консультация → настоящая заявка (после надёжного AI-1)
- Собрать только необходимые поля: марка/модель/год, симптом, код ошибки, система и согласованное местоположение; возможность «не знаю». Учитывать сообщения о критической безопасности.
- На основании явного выбора пользователя предложить консультацию, мастера, эвакуатор, СТО или стационарный ЭБУ. Наличие и специализацию **всегда** подтверждает backend, а не текст LLM; не выдумывать ETA/стоимости.
- Передать диагноз как **черновик** в существующий flow PR #169, показать выбранные поля и получателей, запросить согласие владельца и **отдельное согласие на каждую платную работу**. Водитель не принимает лишние финансовые обязательства. Действующие заказы/платежи не изменяются автоматически.
- E2E: EBS/тормоза → безопасный отказ от опасной инструкции → выбор услуги → consent → новый этап с независимой нумерацией и сметой; повторные запросы не создают дублей.

### AI-3: проверяемая ТехБаза
- Retrieval только опубликованных, лицензированных, технически проверенных материалов с ACL и точной применимостью по ТС/варианту, датой/версией и ссылкой на источник; RAG без прав на текст недопустим.
- Если доказательств нет — «не подтверждено», не выдумывать клеммы, распиновки, схему, диагноз, допуск или стоимость. Кандидатные материалы проходят отдельную человеческую проверку.
- Тесты на смешение похожих вариантов двигателя/EBS, устаревшие документы, закрытые клубы, межролевую утечку и подмену источника.

### AI-4: ИИ в водительском Эфире (позднее)
- Только по `@ТраксБот`/явному действию; человек за рулём не побуждается печатать и читать. Юмор только вне опасных сценариев.
- Не анализировать чужие переписки, не создавать скрытый рекламный профиль, не показывать рекламу под видом экспертной помощи.
- Нужны отдельные договорённости о расходах/провайдере/152-ФЗ/правовых основаниях, метриках ошибок и приёмке.

**AI не блокирует обновление существующей рабочей платформы.** При выключенном флаге весь текущий сервис работает без модели и без создания новых данных/платежей.

## 4. VPS: порядок без опасных операций

### Режим «только диагностика» — можно выполнить на существующем Timeweb
На сервере, без вывода секретов и без автоматического деплоя:

```bash
cd /root/traksos
pwd
git branch --show-current
git rev-parse HEAD
git status --short
cd deploy
bash ./doctor.sh
bash ./diagnose-sms.sh
docker compose ps
```

Обезличить вывод перед передачей. **Не запускать** `git pull`, миграции, пересборку или команды замены контейнера до согласованного release-candidate. Нужны свободное место, статус БД, SHA prod и test, действующий sandbox, исходный и новый образ/digest, HTTPS /api/health, проверка `shop.enabled=false`.

### Gate A — только GitHub
1. Выбрать конкретный состав релиза: **не** объединять PR #111/#152/#168/#169 автоматически. Предрелизный candidate должен иметь проверенные зависимости и не менять утверждённый UI.
2. Проверить GitHub Actions `Проверка`, Android, load и server image на **одном точном кандидатном SHA**; заново после каждого коммита.
3. Проверить миграции сначала на заполненной синтетической БД (в PR #169 уже есть), затем на отдельной **реальной изолированной** копии с документированным пробным restore.
4. Сделать ручную матрицу 390/1440 и физический Android: авторизация, роли, SOS, новые этапы/согласия, статус, отсутствие дублей и переходы.

### Gate B — sandbox на VPS
1. Отдельные база, контейнеры, secrets, домен `sandbox.traksos.ru`; `SMS_PROVIDER=log`, `PUSH_PROVIDER=log`, `PAYMENT_PROVIDER=mock`, магазин закрыт. Тот же SHA/image, что кандидат production.
2. Проверить отсутствие пути от sandbox к production БД, финансы в mock, данные фиктивные; /api/health даёт `sandbox:true`, `db:true`, точный `buildRevision`.
3. Восстановить **копию** резервного архива только в изолированной среде. Убедиться, что старые записи сохранились, индексы и новые связи корректны; проверить повторный запуск штатного мигратора.
4. Никаких автоматических изменений существующего VPS из GitHub без отдельного одобрения и контроля #133.

### Gate C — production только после Gate A+B и ручной приёмки
1. Внешний backup и проверенное восстановление, бэкап непосредственно перед выпуском; `settings.shop.enabled=false` до и после; проверить `.env` без копирования в GitHub.
2. Применять документированный [SERVER_UPDATE_NEXT_CHAT.md](../deploy/SERVER_UPDATE_NEXT_CHAT.md) без `reset --hard`, `down -v`, `pg_restore --clean`, удаления volumes, секретов или ручного «отката» SQL.
3. После: совпадение `buildRevision`, TLS, состояние DB и контейнеров, рабочий вход админа, SMS на своём номере, реальный Android/Push, роли и SOS, магазин закрыт. Финансовые реальные операции остаются выключенными до отдельной банковской/кассовой/юридической приёмки.
4. В #107/#19 записать **фактические** SHA, время, результаты, состояние бэкапа, без пользовательских ПДн. Если gate не пройден — STOP; не объявлять релиз готовым.
