# TrackSOS — агентский доказательный реестр: изолированное ядро

Дата: 2026-11-17. Статус: **Draft / не подключено к боевому магазину**.
Связано с #123, #122, PR #124 (спецификация).
Отдельная ветка: feature/shop-agent-ledger-core-20261117.

## Цель и границы этого PR

Рабочее серверное ядро учёта подтверждаемых событий закупок:
- отдельная неизменяемая классификация каждой строки shop_order:
  клиентское агентирование / агентирование поставщика / собственная перепродажа;
- неизменяемые события с обязательным event_key, контрольным hash, временем,
  ссылкой на доказательство и историей исправлений;
- повторная передача event_key с тем же payload не удваивает суммы, с другим — конфликт;
- частичная корректировка — отрицательная проводка со ссылкой на исходную,
  причиной и ограничением суммы; события хранятся без удаления/перезаписи;
- отдельные суммы закупки, платежей, возвратов, согласованного возмещения,
  комиссий, признанного дохода и входящего/исходящего НДС;
- проверка первички/поручения до закупки/согласованных сумм и классификация
  awaiting_docs, requires_reconciliation, verified, accountant_approved;
- отчёты Москва по дням, календарным неделям (Пн–Вс), месяцам и диапазонам;
  суммы по строкам и компаниям, явная отдельная неподтверждённая часть;
- CSV с нейтрализацией Excel-формул и архивированием снимка + SHA-256;
- сервисный запрет доступа неадминистратору и запись событий доступа в audit_log.

Реализация:
- server/src/services/shopAgentLedgerCore.ts — чистая проверка и расчёт.
- server/src/services/shopAgentLedger.ts — SQL-хранилище, идемпотентность,
  разрешения, журнал аудита, чтение, построение и архивирование реестров.
- server/migrations/200_shop_agent_evidence_ledger.sql — 3 изолированные таблицы.
- server/test/shopAgentLedgerCore.test.ts — тесты арифметики, проверок и доступа.

## Принципиальные ограничения

**Это не готовый раздел административного интерфейса и не рабочий налоговый отчёт**.
Сервис не импортируется в server/src/app.ts, не поднимает HTTP-маршруты,
не открывает настройки магазина и не участвует в checkout/оплате.
Никакой API поставщика не объявлен подключённым; ручной документ нельзя
помечать подтверждённым без реальной проверки и защищённого первичного файла.

Только события типа recognized_revenue образуют колонку собственного признанного
дохода; **она не равна** retail - purchase и не рассчитывается автоматически
из 30% + 5%. Эти ставки — незакреплённые коммерческие ориентиры, не налоговая
ставка и не автоматически подтверждённое агентское вознаграждение.

Поле source_kind=primary_document_verified требует SHA-256 и защищённую ссылку,
но само по себе **не проверяет содержимое первичного файла**. Для реального
выставления статуса в production нужен отдельный workflow сверки документа,
с привязкой защищённого файлового хранилища, правами бухгалтера, электронными
подписями и проверкой суммы/количества по каждой строке. Иначе импортировать
документы только как manual_unverified.

Статус accountant_approved означает наличие *заявленного* события подтверждения
со ссылкой на подписанное доказательство. Нужна юридически действительная
проверка полномочий подписанта и валидности подписи до UI.

Для supplier_sales_agent возможен исключительно дальнейший отдельный юридически
утверждённый сценарий с договором поставщика. Сейчас расчёт общей схемы
зафиксирован технически, но не предназначен для боевого автоматического учёта.

Timezone Europe/Moscow сейчас UTC+03:00 (периоды привязаны к полуночи МСК);
изменение законодательных правил времени потребует отдельного обновления
конвертации, не корректировки старых снимков.

Схема дополняет, но **не заменяет** payment_capture_intents,
partner_finance_entries, shop_orders или платёжную бухгалтерию. Нельзя
копировать события банка в ledger без проверенной системы соответствия
и событий идемпотентности. Закупочный API «Автоконтинента» отсутствует.

## Перед подключением к админке и боевым деньгам

1. Юрист/бухгалтер утверждают отношения сторон, агентское поручение,
   формулу комиссий, базу и момент признания дохода, НДС/УСН.
2. Формализовать адаптеры shop_order_line_id, payment_id, поставщика,
   первичных документов/УПД и доверенного сервиса проверки их хешей.
3. Применить миграцию к отдельной disposable test DB, прогнать
   PostgreSQL integration, исправления/конкуренцию/восстановление/бэкапы.
4. Подключить только admin ACL и утверждённый дизайн «Финансы → Реестры»;
   запретить утечку закупочных полей в публичный каталог, индекс, APK.
5. Проработать multi-line allocation одного УПД, количественные частичные
   поставки и документированные закрытия периода. В этой версии ещё нет
   достаточных полей для налогового пакета и XLSX/PDF.
6. Провести сквозную приёмку с бухгалтером. До этого не размещать PDF
   «для ФНС» и не отправлять декларации в государственные сервисы.
