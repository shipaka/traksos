# TrakSOS — ручной безопасный выпуск на VPS

Этот регламент относится к workflow `.github/workflows/deploy-vps-manual.yml`. Он **не** публикует изменения при merge в `main`. Релиз запускается только вручную, с SHA и фразой `RELEASE TRAKSOS`.

## Что уже проверено

Read-only SSH-аудит 20.11.2026 (GitHub Actions run 44807410175) подтвердил доступ к VPS с pinned Ed25519 host key, рабочие production app/db и отдельную sandbox app/db. На сервере была ревизия `a380f197aa272c2b2e065a6a725149b8fa278c33`, в центральном GitHub она не разрешалась. Это **блокер**, а не повод сделать `reset --hard`.

## Доступы и секреты

В GitHub Actions действуют уже использованные read-only секреты `TRAKSOS_VPS_HOST`, `TRAKSOS_VPS_HOST_KEY` и `TRAKSOS_VPS_READONLY_KEY`. В отличие от них, для выпуска требуется **отдельный** `VPS_SSH_KEY`, чей публичный ключ уполномочен на разрешённые команды на VPS. Секреты `VPS_HOST`, `VPS_USER`, `VPS_KNOWN_HOSTS` необязательны: workflow использует существующий хост, его известный pinned Ed25519 key и пользователя `root`, если альтернативы не заданы.

Ключ для чтения **не может** использоваться как ключ выкладки. Не присылайте ключи, пароли или содержимое `authorized_keys` в обсуждения или PR. Условия доступа к production environment, включая требуемых проверяющих, настраиваются в **Settings → Environments → production**. Из кода нельзя подтвердить, что ограничения и секрет на запись действительно уже настроены.

## Предрелизные условия

1. Утверждённый интерфейс и нужные функциональные PR уже интегрированы в `main`; нужный точный SHA имеет зелёные сборки, браузерные прогоны и Android-проверки. Не выпускать старый `main` вместо ожидаемой версии.
2. Снять независимый резервный снимок/бэкап VPS и БД и убедиться, что его можно восстановить, **до** устранения расхождения историй.
3. На VPS выяснить, как возник `a380f197…`: проверить `git log`, `git status`, `git remote -v`, `git merge-base` и отличия от `origin/main`; сохранить все локальные изменения. Не делать `reset --hard`, `git clean -fd`, удаление Docker volumes, таблиц или учётных записей.
4. Согласовать чистую `main` с происхождением из `shipaka/traksos`. Выпуск допустим **только если текущий HEAD VPS — предок требуемого `origin/main`**. При расхождении workflow остановится без перезапуска production.
5. Проверить отдельный SSH deployment key и pinned host key, существующий отдельный sandbox в `/root/traksos-sandbox/deploy`, без общего volume PostgreSQL с production.

## Запуск

Открыть GitHub → Actions → **TrakSOS — безопасный выпуск на VPS** → Run workflow (branch: `main`); указать полный 40-символьный текущий SHA `main`, поле подтверждения `RELEASE TRAKSOS`. Отдельный workflow `TrakSOS — проверка безопасности релизного workflow` не требует секретов и валидирует YAML, Bash и fail-closed ограничения перед merge.

Workflow проверяет SHA `main`, SSH и pinned key, origin и fast-forward, затем вызывает `deploy/update-site.sh`: дамп PostgreSQL и проверка архива, сборка приложения, проверка новой сборки на существующей изолированной песочнице, обновление только контейнера приложения и health. После этого он требует маркер фактически завершённого удалённого сценария и проверяет `https://traksos.ru/api/health`: `db=true`, `sandbox=false` и `buildRevision` точно равен запрошенному SHA. Если forced-command ключ просто вернёт `status`, выпуск не будет признан успешным.

## В случае отказа

Не повторять deploy вслепую. Проверить конкретный остановившийся шаг и состояние VPS. Ошибка до `docker compose up ... app` означает, что рабочий контейнер не должен был заменяться; Git checkout мог уже продвинуться при успешном `--ff-only`. Ошибка **после** замены app может потребовать ручного восстановления, совместимого с миграциями; не откатывать БД автоматически и не подставлять старый образ без анализа схемы. Сохранять логи, бэкап и SHA сборки.

Слияние этого операционного PR в `main` **не означает**, что сайт опубликован, что ключ на запись существует или что VPS-история согласована.
