## 2. Что уже в `main`, но не равно «работает на Timeweb»

- **[#97](https://github.com/shipaka/traksos/pull/97)**: ручная регистрация номера администратором, назначение допустимых ролей и SMS-активация владельцем номера.
- **[#98](https://github.com/shipaka/traksos/pull/98), [#99](https://github.com/shipaka/traksos/pull/99)**: обращения разработчику через админку, внутренняя очередь, повторяемый закрытый webhook, статусы. Для *фактической* доставки нужен настроенный приватный HTTPS-получатель.
- **[#101–104](https://github.com/shipaka/traksos/pulls?q=is%3Apr+is%3Amerged+101+102+103+104)**: страховые статусы, карточки в гараже и на главной, очередь страховщика и мобильные действия. Проверены реальные тестовые экраны; **не подтверждено** оформление полисов/оплата у реальных страховых компаний.
- **[#105](https://github.com/shipaka/traksos/pull/105)**: интеграция единого sandbox/реальных кабинетов, диагностических экранов, GPS-логов, одноразового входа, мобильного демо, честных настроек заявок; код в `main`. Фактический запуск sandbox на VPS ещё НЕ подтверждён.
- Документ будущей бренд-программы существует; **ничего брендированного партнёрам публично не обещано**.

Общий принцип: GitHub `main` ≠ зелёная сборка `main` ≠ загруженная версия на Timeweb ≠ готовность к публичным оплатам/RuStore.

## 4. Блокеры, которые не решит один GitHub merge

- **Timeweb:** обследование текущего VPS, совпадение SHA, резервная копия и тест восстановления, миграции, HTTPS, логин администратора, магазин по-прежнему `enabled=false`. Инструкция: [SERVER_UPDATE_NEXT_CHAT.md](../deploy/SERVER_UPDATE_NEXT_CHAT.md).
- **SMS.ru и Т-Мобайл:** реальную доставку и восстановление на собственном номере проверить на *живом* VPS; настройка оператора ≠ факт доставки.
- **RuStore Push / Android:** сборка debug APK ≠ проверка получения звонка на заблокированном телефоне и подписанного релизного APK.
- **ЮKassa/деньги:** реальные платежи, чеки, возвраты и выплаты не включать до завершения финансового P0 и проверки договоров.
- **Автоконтинент:** витрина и локальные справочники есть, но прямой API, актуальные цены/остатки, лицензированные кроссы и VIN-применяемость **не подтверждены**. См. [SHOP_CATALOG_LOW_DATA.md](SHOP_CATALOG_LOW_DATA.md).
- **Pampadu / юридические лица / лизинг:** ручной страховой сценарий ≠ проверенная интеграция брокера и подтверждённые условия страховых.
- **Телефония:** подменные номера, запись, сроки хранения и согласия требуют реального договора/интеграции и теста.
- **152-ФЗ, договоры, хранение и оферты:** нужна проверка оператора данных, юриста, размещения/резервных копий и реальных потоков данных.
- **Погода:** реальный API Яндекса и ключ на VPS плюс fallback; не считать наличием рабочего API только графику сезонов.

## 5. Правила для следующего разработчика / чата

1. **В первую очередь открыть этот файл**, затем GitHub `main` HEAD, Actions, issues #107/#19/#90 и **архив объединения PR #105**. Не полагаться на зафиксированный SHA без свежей сверки.
2. **В работу одновременно не более одного крупного интеграционного PR на каждую область**. Старые DRAFT — справочник и исходные изменения, не очередь «слить всё подряд».
3. Перед закрытием Issue указать: какие требования выполнены, тест/скрин/коммит/PR и результат на VPS, если задача про производство. Без доказательства — «частично» или «не подтверждено».
4. Перед закрытием старого PR проверить file-by-file, что нужная логика действительно есть в принятом PR или `main`. Закрыть как superseded с ссылкой на замену; **не удалять ветки вслепую**.
5. Проект не готов к реальным деньгам или публичному запуску только потому, что GitHub показывает зелёный CI. Живые SMS, платежи, push, юридические документы и Timeweb — отдельные контрольные условия.
6. Приоритет — **довести существующий утверждённый продукт до работающего выпуска**, не предлагать новые большие функции, пока P0 не закрыты.

**Где писать результат:** комментарии по соответствующему Issue; для запуска — [#19](https://github.com/shipaka/traksos/issues/19), для интеграции кабинетов — [#90](https://github.com/shipaka/traksos/issues/90)/[#105](https://github.com/shipaka/traksos/pull/105), для денег — конкретный P0 Issue. Не дублировать одинаковые задачи во всех чатах.

## 7. Магазин СПб и собственная курьерская доставка (добавлено 16.11.2026)

Дополнение к общей задаче [#110](https://github.com/shipaka/traksos/issues/110). Отдельный [документ: региональность, курьеры, GPS, прибыльность и предрелизный STOP](SHOP_COURIER_LAST_MILE_AND_PRICE_2026-11-16.md). Всей России — бренд, сервисы и сообщества; **продажа запчастей только Санкт-Петербург**, другие города видят «Пока недоступен в вашем регионе». Собственных курьеров добавляет администратор, доставки группируются в проверяемые рейсы, покупатель видит GPS своего курьера, а не чужие остановки. До открытия магазина обязательно пересчитать закупку Автоконтинента, наценку, 5% сбор, логистику и конкурентов **при равном сроке получения**. Ни этот документ, ни миграция не означают готовность курьерского кабинета; визуал согласовать отдельно.


**Утверждено 16.11.2026:** закупочная цена Автоконтинента плюс **минимум 30% наценки**, отдельно от 5% комиссии TrakSOS; обоснованные исключения только по артикулу с доказанной конкурентной ценой и сроком. Реальные события поставщика сохраняются и выводятся в историю заказа; отмена без причины не является возвратом. [Расчёт и источник статусов](SHOP_COURIER_LAST_MILE_AND_PRICE_2026-11-16.md).

## 12. Подтверждение передачи курьером: PIN + действие клиента (16.11.2026)

В draft PR #111 теперь реализована схема **«прибытие → покупатель создаёт шестизначный код → назначенный курьер вводит код на активной остановке → покупатель лично подтверждает полученный товар»**. Не выдавать прибытие или ввод кода за завершение передачи. Сервер хранит scrypt-хеш с солью, ограничивает 5 попыток, код действует 10 минут, перевыпуск через 30 секунд; после завершения или невручения секрет удаляется, а в хронологии остаётся только событие `handoff_verified`. Комиссию и выплату это само по себе не проводит. Курьер не видит соседние заказы, закупку или PIN из аккаунта покупателя.

**Не закрыто:** альтернативный подтверждённый документ для получателя без смартфона, реальный акт сверки/фото пакета с правами доступа и согласием, правила урегулирования ошибочного PIN/подмены получателя, проверка пользователем на физическом Android; все старые P0 по Автоконтиненту, схеме цен, банку и курьерским маршрутам остаются. Веб и Android CI необходимо получить по актуальному SHA перед объединением.

## 14. P0 — безопасный федеральный SOS без фальшивого тарифа СПб/ЛО (16.11.2026)

**Выполнен первый технический защитный слой в [PR #111](https://github.com/shipaka/traksos/pull/111):**
- `server/src/domain/pricingRegion.ts`: осторожный фильтр по координатам для отсечения **явно** удалённых городов и регионов. Широкая рамка вокруг СПб/ЛО — **не точный геокодер, не полигон покрытия и не доказательство зоны**. Если координаты или текст адреса явно указывают на Москву, Калининград, Владивосток, Ижевск, Псков и др., расчёт старого тарифа блокируется; противоречивый адрес тоже отклоняется.
- `POST /api/pricing/estimate` получает указанные клиентом координаты и адрес, возвращает `regionValidation` с честным `validatedByGeocoder:false`, `manualConfirmationRequired:true` для неизвестных адресов, а для **явно чужой географии** — `409 outside_legacy_tariff_region`. Публичные ложные тарифы не показывать.
- `OrdersService.create` выполняет такую же проверку для реальной заявки **до создания заказа, банковского холда, уведомления исполнителей и диспетчеризации**. На явно чужой географии запрет в самом сервере, не только скрытая клиентская кнопка. Созданные исторические заказы, статусы и замороженные платежи не перерасчитываются.
- `NewOrder` больше не выбирает `zoneId='spb'` автоматически при открытии формы (кроме независимой телефонной консультации): пользователь выбирает действующую локальную тарифную зону. GPS запрашивается **только по кнопке**, не при открытии формы. Калькулятор учитывает указанный адрес/точку, показывает предупреждение, не допускает отправку пока расчёт не сформирован; согласие на сумму сбрасывается при смене зоны.
- `server/test/pricingRegion.test.ts` проверяет несколько чужих городов, противоречивый GPS/адрес, невозможность прямого API-обхода, отсутствие банковских холдов и диспетчеризации, сохранение локального заказа и федеральной консультации без выезда.

**Остаётся P0 и [issue #113](https://github.com/shipaka/traksos/issues/113) НЕ закрывать:** без лицензированного геокодера, точного полигона доступности и проверенных региональных расценок нельзя ни автоматически определить, что неизвестный адрес реально входит в зону, ни подтвердить конкретную тарифную зону, ни обещать выезд по России. `manualConfirmationRequired` сейчас предупреждение, **не доказательство географии**. Серверный старый контракт для запросов без геоданных пока не закрыт в пользу нового ручного оформления; полное решение нужно согласовать и протестировать отдельно, не разрушая старые клиентские/API-сценарии и платежи. **Не считать блокер закрытым из-за одного прямоугольника на карте.**

Связанные незакрытые задачи остаются в этом документе: финальная кинематографичная общероссийская главная и карты, визитки/выездные исполнители, Эфир, ТехБаза, реальные магазинные закупки Автоконтинента, прибыльность и собственные курьеры (только СПб), ручное подтверждение передачи без смартфона, звонилка/подменные номера, банк, гарантии, оспаривания, стабильная APK.


## 15. Защита предварительной цены и водительских приглашений — продолжение PR #111 (17.11.2026)

**Код в черновой ветке, не финальное подтверждение релиза.**

- В `NewOrder` клиентское согласие и отображаемый расчёт привязаны к **точным параметрам**: услуга, класс, тарифная зона, ночной коэффициент, групповой выезд, адрес и GPS. При изменении параметров или во время 350-мс ожидания адреса старая оценка и согласие не могут использоваться для подачи заявки. Это в том числе защищает ввод адреса из предварительного заполнения.
- `legacyTariffZoneMismatch` в `pricingRegion.ts` консервативно выявляет **явно названные** Гатчину, Тосно, Выборг, Лугу, Кириши и Усть-Лугу, когда клиент выбирает тариф **другого** муниципалитета. Одинаковый контроль в публичном расчёте и непосредственно при создании заявки, до денег и диспетчеризации. Сервер отвечает `409 mismatched_legacy_tariff_zone`; цену за клиента автоматически не меняет.
- Названные административные субъекты России (например, Республика Карелия, Приморский край) нельзя выдавать за Ленинградскую область, **даже если** присланы подложные GPS-координаты из широкого прямоугольника СПб/ЛО. Явные чужие регионы возвращают `409 outside_legacy_tariff_region`.
- Водительские запросы на личную переписку остаются идемпотентными. При повторных запросах одной пары водителей не отправляются новые приглашения/уведомления; конкурирующие повторения проверяются в `communityDirect.test.ts`.
- В **общем Эфире и личных сообщениях** повтор того же `clientNonce` теперь возвращает сохранённое сообщение **без нового уведомления** в реальном времени. Иначе сетевые повторы на слабой связи создавали бы дублирующий сигнал при одной записи в базе. Защита действует и при конкурентных запросах, проверяется в `community.test.ts` и `communityDirect.test.ts`.
- `server/test/pricingRegion.test.ts` расширен случаями именованных муниципалитетов, подложного GPS, правильной местной зоны и отсутствия новых платёжных холдов для неверного тарифа. В `server/test/communityDirect.test.ts` добавлен конкурентный повтор приглашений.

**P0 #113 остаётся открытым:** это только защита от очевидных несоответствий; подтверждённого геокодера, точных полигонов КАД/ЛО, региональных тарифов, серверной обязательной верификации **неопределённых** адресов, безопасной ручной сметы и полной приёмки существующих API-клиентов ещё нет. По данным без доказанной географии старое API пока может вернуть предварительную цену с предупреждением. Не включать федеральные платные выезды; не выдавать наличие контактов в «Помощи рядом» за тариф, бронь или успешную оплату. Магазин — только Санкт-Петербург, по-прежнему выключен до отдельной приёмки.

## 16. P0 — упорядоченные события Эфира и модерация после курсора (#114, 17.11.2026)

**Реализовано в Draft PR #111, не означает разрешения на массовый запуск:**

- Миграция `129_community_moderation_events.sql` создаёт **два изолированных журнала событий** для комнат и личных диалогов; в них нет текста, телефонов или GPS, только ID сообщения, предыдущий/новый статус и время. Удаление сообщения удаляет связанные события.
- Новые **опубликованные** сообщения и решения модератора фиксируются в этих журналах в той же транзакции, что и сообщение или изменение статуса; операции сериализуются блокировкой строки комнаты/личного диалога. Поэтому более поздний event cursor не опережает фиксацию более раннего события **в том же канале**, в отличие от одних только `message_id`.
- `GET /api/community/rooms/:id/messages` и `GET /api/community/direct/:id/messages` выдают `moderationCursor`, взятый **до** чтения исходных последних сообщений; случайные изменения во время запроса воспроизводятся по независимому курсору.
- `GET /api/community/rooms/:id/moderation-events` и `GET /api/community/direct/:id/moderation-events` возвращают ограниченные страницы `changes,nextCursor,hasMore`. Чужие закрытые комнаты и личные ветки скрываются серверным ACL; отказанные pending-сообщения **не раскрываются другим участникам**, но их курсор двигается. Скрытые публикации доставляются как tombstone без исходного текста.
- Решение модератора идемпотентно по статусу: повторное утверждение **не генерирует второй event**. При параллельной модерации одного канала срабатывает последовательная запись и транзакционный журнал с аудитом.
- `driverAir.tsx` обновляет **не только новые сообщения**, но и поздние одобрения и скрытия; слушает push-like live сигнал без передачи содержания, проверяет изменения при переподключении, в памяти держит максимум 160 сообщений и до 10 поздних одобрений, не пишет личные чаты в localStorage.
- Добавлены серверные тесты `community.test.ts` и `communityDirect.test.ts` на публикацию позади старого курсора, немедленное скрытие, конкурирующие решения, раздельную аудиторию и отсутствие утечек содержимого.

**Открытые условия приёмки:** новый CI **на актуальном SHA**, эмуляторы Android API 29/35, физические телефоны и реальный слабый интернет, тест восстановления после долгого офлайна (более 500 накопившихся событий), проверки политики хранения журнала, доступности/нагрузки больших комнат, отзыв ролей, блокировки, локальный часовой пояс и дизайн. - `partnerActivity.ts`: собственные предложения за последние 90 дней из `order_dispatch`, только личная история; 13–14 календарных недель по UTC, завершения этих предложений и объявленные часы online/on_call без паузы, вычисленные из `partner_presence_events`. Отдельная отметка, если история наблюдений началась позже окна.
- `GET /api/partner/activity` доступен только исполнителю, `GET /api/admin/partner/activity/:id` — администратору. В действующем кабинете Партнёра появился недельный отчёт с предупреждением, что смена статуса без GPS/heartbeat не доказывает физическое присутствие. Нельзя экстраполировать личные предложения на всех доступных заказчиков города.
- Результат **не меняет** уровень, очередь выдачи, комиссию, бонусы, выплаты, санкции. Проблема низкой выборки явно маркируется, не трактуется как отказ работать.
- `server/test/partnerActivity.test.ts`: защита личных данных и ролевой доступ, две реально личные диспетчерские отправки, 3 часа объявленного присутствия, отсутствие вымышленной статистики.
- **Открытая задача #119:** настоящие сравнимые когорты по району/сезону/специальности и фактической готовности после достаточной выборки, отдельная ручная экономическая приёмка.

## 23. Складская сверка запчастей перед выдачей курьеру

- `135_shop_warehouse_line_verification.sql`: на **новом** курьерском рейсе может быть вручную включён флаг `packing_required` (по умолчанию false); независимые строки `shop_warehouse_line_checks` с индексом товара, артикулом, проверенным количеством, оператором, временем, способом и обоснованием ручной сверки.
- `shopWarehouse.ts`: admin-only просмотр состава рейса **без цен/закупки/GPS/адресов и личности клиента**, проверка фактического артикула и пересчитанного количества против сохранённого состава заказа; ошибки и неполные артикулы блокируют подтверждение. На каждое действие отдельный audit event; корректировки доступны только до утверждения отправки.
- `shopCourier.ts` и `shopCourierEconomics.ts`: если администратор включил строгую комплектацию, нельзя утвердить отправку и нельзя забрать конкретную посылку, если её строки не сверены или товар заменён после проверки. В уже созданных маршрутах этот флаг **не включается задним числом** и исходные статусы/деньги не изменяются.
- `courierWarehouse.tsx` и `courierAdmin.tsx`: формы для ввода/сканирования маркировки и физического пересчёта с видимыми блокерами, обязательным пояснением без сканера и журналом проверок. USB/HID-сканер работает как клавиатура в поле; **ещё нет** аппаратной аттестации «действительно отсканировано», GS1/EAN, штрихкод-номер партии или отдельной роли кладовщика.
- `server/test/shopWarehouse.test.ts`: блок неправильного SKU/qty, запрет редактирования после отправки, инвалидация проверки после подмены артикула, доступ администратора и отсутствие персональных данных. Ничего не включается для публичного магазина: стоп-релиз #107 остаётся.
- **Открытая задача #118:** реальная интеграция устройства сканирования, серийные номера/партии, склад, Автоконтинент, контроль недовложения/брака/возврата и физический Android.

## 24. Режим пакетного выполнения без простоя на CI

**Принцип по поручению владельца:** одновременно движемся по независимым ветвям функционала внутри изолированного Draft PR, помечаем точный HEAD, отправляем серию содержательных коммитов и запускаем CI. Пока PostgreSQL, npm, Android и browser E2E выполняются — берём следующий независимый модуль; затем проверяем **только последний коммит**, собираем сбои по шагам и исправляем одной серией. Не объявлять предыдущие зелёные прогоны доказательством готовности нового HEAD.

**Не считать „разрабатывается“ равно „развёрнуто“:** main и Timeweb без изменений до #107; старые PR #108 и дизайн #112 не смешивать. Полная программа #110 и ТехБаза #116 содержат ещё значительно больше работ, чем эти три пакета; интерфейс всех новых кабинетов должен быть отдельно принят в премиальном дизайне.
