# Офлайн-обработка стендовых журналов
Добавлено диагностическое ядро для приема уже собранного полного UDS PDU (не CAN-кадра). Оно не подключается к прицепу, не отправляет запросов и не очищает память. В Android реализован UI ручного импорта уже записанных ответов. Физический сбор журналов ESP32 ещё отсутствует. Формат комплекта для офлайн-проверки: bench-evidence-package.md.

Для каждой записи хранить: источник (синтетический или ручной стендовый импорт), производитель и семейство, полный номер детали, версия ПО, время наблюдения, маска выбора статусов фактического запроса (если известна), полный исходный PDU. Не включать личные данные/госномера/VIN. Метаданные номера детали и версии должны быть сверены с маркировкой/эталонным инструментом, не угадываться из CAN-ID. Для транспортного анализа отдельный необработанный журнал должен содержать время, направление, идентификатор кадра, DLC, данные и сведения об интерфейсе; этот парсер сырые CAN-кадры не принимает.

Пример СИНТЕТИЧЕСКОГО PDU: 59 02 49 AB CD EF 09. Не реальный код модулятора. Для отрицательного ответа 7F 19 78 результат остаётся отрицательным, а не «ошибок нет». Невалидный ввод отклоняется. Сырые байты сохраняются в положительном и отрицательном ответе. Каталог по умолчанию пуст. Только точно совпадающие семейство, номер детали и версия ПО могут получить проверенный профиль; синтетические данные не получают рабочую расшифровку.

Сравнение до/после: требуется подтверждение, что это один физический ЭБУ, совпадающие идентификация, источник и фильтр статусов, маска доступности, корректный порядок времени, два положительных отчёта. Сравниваются добавленные/исчезнувшие записи и изменившиеся байты статуса. Исчезновение записи не доказывает ремонт. Подтверждение одного ЭБУ предоставляется испытателем, не выводится из номера детали. Не использовать сравнение как допуск к эксплуатации. Реальные профили, совместимость транспорта и подтверждённые команды остаются отдельным этапом.
