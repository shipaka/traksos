# Комплект стендовых доказательств TrakSOS Mini Diagnostic
## Назначение
Подготовить материалы для проверки одного конкретного ЭБУ, не выдавая справочные коды или синтетические тесты за подтверждение совместимости. Пока собственное устройство не готово к физическому подключению, допустим только анализ уже полученных материалов с согласованного неподвижного изолированного стенда и штатного диагностического оборудования. Этот инструмент не снимает журналы самостоятельно и не даёт инструкций по подаче питания. Не выполнять очистку, активацию тормозов, калибровки или изменение параметров для получения записей.
## Состав одной сессии
Отдельная папка на каждую комбинацию фактического ЭБУ, версии ПО и сессии. Сохранять исходные файлы без редактирования, не помещать в пакет персональные данные, VIN, номера ТС, чужие журналы или файлы с секретами. Если требуется обезличивание, хранить исходник отдельно и явно указывать происхождение копии в notes.txt. 
- manifest.json: метаданные, декларации испытателя, список файлов с контрольными суммами.
- identity.txt: ранее записанные ответы идентификации; указать точный формат, не придумывать значения.
- dtc.txt: ранее записанные диагностические ответы; указать протокол и фильтр, если известны.
- reference.txt: текстовый экспорт/сверка с заводским инструментом, с его точной версией. Не заменять собой исходный экспорт.
- notes.txt: состояние стенда, метод записи, известные ограничения, направление/адреса, время, сведения о кабеле. Неподтверждённое явно обозначать.
- trace.log: для CAN — журнал классического CAN компактного формата candump; иные форматы не считаются проверенными данным инструментом.
- label.jpg: необязательная фотография маркировки (только если безопасно и разрешено). Программа проверяет только целостность файла, не изображение.
## Проверка
1. Сформировать список размеров и SHA-256: `python tools/bench_evidence.py inventory SESSION` из mini-diagnostic.
2. Заполнить manifest.json по шаблону ниже. Добавить kind к каждой строке инвентаря. Все файлы папки, кроме самого манифеста, должны входить в список. Нельзя использовать вложенные папки или символические ссылки.
3. Проверить: `python tools/bench_evidence.py check SESSION --output REVIEW.json`. Выходной файл должен быть вне SESSION и ещё не существовать. Код возврата 0 — структурная готовность к ручной проверке, 2 — неполный/синтетический/нечистый комплект, 1 — неверный формат или нарушение целостности. 
4. Сверять вручную номер, аппаратную и программную версию, исходные ответы, эталонную расшифровку и выбранный транспорт. Не создавать профиль автоматически. Отдельно подтвердить физический интерфейс и аппаратную защиту.
## Шаблон манифеста (синтетический, НЕ готов к реальной проверке)
```json
{
  "schema": "traksos.bench-evidence.v1",
  "session_id": "example-01",
  "origin": "synthetic",
  "observed_at": "2026-11-26T12:00:00+03:00",
  "target_id": "zf-tebs-e",
  "part_number": "unknown",
  "hardware_version": "unknown",
  "software_version": "unknown",
  "reference_tool": "unknown",
  "reference_tool_version": "unknown",
  "interface": "UNKNOWN",
  "cable_id": "unknown",
  "read_only": false,
  "isolated_stationary_bench": false,
  "source_reviewed_by_operator": false,
  "files": []
}
```
Разрешённые kind: can_trace (.log), identity_responses (.txt), dtc_responses (.txt), reference_report (.txt), notes (.txt), label_photo (.jpg). Запись каждого файла: name, kind, bytes (целое число), sha256 (64 строчные шестнадцатеричные цифры). interface: ISO11992, ISO11898, K_LINE, UNKNOWN. origin: synthetic или manual_bench. Декларации не подтверждаются автоматически. Структурная проверка не удостоверяет происхождение, содержание текстового отчёта, изображение или точность профиля. Не поддержаны JED 677/J1587/PLC и другие типы журналов как отдельные транспортные форматы. Приоритет первых будущих образцов — TEBS E/D, Knorr G2, VIE, Haldex EB+, современные iEBS и SORL TEBS. Все флаги подтверждения источника, профиля и разрешения активной диагностики всегда false в автоматическом отчёте.
