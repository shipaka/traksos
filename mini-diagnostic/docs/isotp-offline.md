# ISO-TP: офлайн-сборка диагностического ответа
Источники: Linux Kernel ISO 15765-2 https://kernel.org/doc/html/latest/networking/iso15765-2.html ; описание адресации и примеры формата https://can-isotp.readthedocs.io/en/latest/isotp/addressing.html ; ограничения длины и тайм-аутов https://can-isotp.readthedocs.io/en/latest/isotp/implementation.html . Изучены HTML-источники, полный нормативный текст ISO не проверен.
Реализован строго ограниченный декодер: классический CAN, normal addressing, только data frames до 8 байт; SF 1–7 байт, FF с 12-битной длиной 8–4095, CF с проверкой номера и циклическим переходом 15→0. Проверяет совпадение идентификатора, standard/extended ID и интерфейса, хронологию и заданный инженером максимальный интервал, отсутствие лишних кадров, полноту. Нужна заранее выделенная последовательность одного ответа. FC в этой последовательности не принимается: управление потоком, подтверждение соблюдения FC, STmin и block size не реализованы. Padding не валидируется. Не поддерживаются CAN FD, расширенная/смешанная адресация и 32-битный FF length. 29-битный ID сам по себе не означает extended addressing.
IsoTpUdsImport связывает собранный PDU с существующим офлайн-декодером UDS ошибок. Сохраняет raw PDU, не устанавливает семейство или адрес ECU автоматически. Исходный журнал и происхождение сохранять отдельно. Синтетические тесты включают 4095 байт, циклическую нумерацию, потерю, повтор, неправильную последовательность, чужой ID и разбор двух искусственных DTC.
Это не активная реализация ISO-TP и не доказательство использования ISO-TP любым прицепным блоком. ISO 11992-4, KWP, JED, J1939 и фирменные протоколы не считать взаимозаменяемыми. Никаких команд передачи, подключения к BLE/CAN или реальной очистки. Подтверждать электрический интерфейс, транспорт и профиль каждой ревизии отдельно.
